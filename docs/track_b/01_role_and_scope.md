# Track B 팀원 D 역할 및 업무 범위

> 작성일: 2026-08-28

> 전제: 최소 표본을 받기 전에 착수할 수 있는 업무를 우선 정의한다.

## 1. 문서 목적

이 문서는 Track B 팀원 D가 담당할 Fine-tuning 및 생성·개인화 업무의 범위를 정한다. 팀원 사이의 중복 작업을 줄이고, 데이터 표본이 준비되기 전에도 설계 작업을 시작할 수 있도록 책임, 비책임, 협업 지점을 구분한다.

이 문서는 Fine-tuning 모델의 최종 채택을 미리 결정하지 않는다. Prompt Baseline과 Fine-tuning 모델을 같은 조건에서 비교한 결과에 따라 채택 또는 미채택 의견을 제시하는 것까지를 D의 책임으로 본다.

## 2. D의 업무 목표

> 검색된 동일한 근거를 사용해 `쉽게`, `일반`, `깊이 있게` 수준의 답변을 일관된 형식으로 생성하고, Prompt Baseline과 Fine-tuning 모델을 동일 조건에서 비교하여 Fine-tuning의 필요성과 효과를 설명한다.

Fine-tuning은 역사·문화 지식을 모델에 암기시키는 용도로 사용하지 않는다. 문서 지식과 출처는 RAG가 담당하고, D는 다음 생성 행동의 개선 가능성을 검증한다.

- 설명 수준에 맞는 표현
- 합의된 응답 형식 준수
- 검색 근거 밖 내용의 생성 억제
- 근거가 부족할 때 답변을 보류하는 표현
- 딱딱한 원문을 자연스럽게 설명하되 사실과 출처를 유지하는 행동

## 3. D의 직접 책임

| 영역 | 책임 | 주요 산출물 |
| :--- | :--- | :--- |
| 목표 행동 정의 | Fine-tuning으로 개선하려는 행동과 성공 기준 정의 | 역할 정의서, 목표 행동 목록 |
| Prompt Baseline | Fine-tuning 전 비교 기준이 되는 Prompt 설계·버전 관리 | Prompt Baseline 문서와 템플릿 |
| 생성 응답 규격 초안 | 생성 모듈이 반환할 구조화된 응답 형식 제안 | 응답 스키마 초안 |
| 생성 컴포넌트 | 검색 결과를 입력받아 Prompt → Model → Parser를 수행하는 독립 모듈 | 생성 코드와 단위 테스트 |
| 학습 데이터 설계 | 학습 예제 형식, 작성 기준, 검수 상태, 데이터 분리 기준 설계 | 학습 데이터 명세와 검증 규칙 |
| Fine-tuning | 승인된 데이터와 모델을 사용한 학습 및 실험 기록 | 학습 설정, 모델 식별 정보, 실행 결과 |
| 전후 비교 | 동일 평가 세트와 고정 조건을 사용한 Baseline 대비 비교 | 비교표, 실패 사례, 비용·성능 분석 |
| 채택 의견 | 결과에 근거한 적용·미적용 또는 추가 실험 의견 작성 | Fine-tuning 채택 판단안 |

## 4. 초안 역할의 반영 범위

초안의 `Prompt`, `응답 스키마`, `RAG Chain` 중 다음 내용을 D의 업무에 반영한다.

| 초안 업무 | 반영 방법 | 최종 책임 |
| :--- | :--- | :--- |
| Prompt | Prompt Baseline과 수준별 개인화 Prompt로 유지 | D |
| 응답 스키마 | D가 초안을 만들고 C·E·F와 인터페이스를 합의 | D 초안, 공동 승인 |
| RAG Chain | 팀 역할표상 E의 주 담당을 유지한다. D는 생성 구간을 구현하고, 비교 목적의 실험용 RAG Chain 후보를 별도로 만들 수 있다. | E: 운영·통합 Chain, D: 생성 구간·실험 후보 |

D가 구현하는 생성 컴포넌트는 다음과 같은 경계를 가진다.

```text
C의 Retriever 결과
        ↓
D의 생성 컴포넌트
Prompt → Model → Output Parser
        ↓
E의 RAG Chain·근거 판정·안전장치
        ↓
F의 Streamlit 화면
```

위 구조는 팀 회의에서 정한 역할을 변경하기 위한 것이 아니다. E의 `RAG Chain·LLM·안전장치·통합 평가` 주 담당과 D의 `Fine-tuning 데이터·모델 학습·비교` 주 담당을 그대로 유지한다.

시간 제약이 있으면 D와 E가 하나의 RAG Chain 설계를 모두 합의할 때까지 기다리지 않고 각자의 후보를 병렬로 구현할 수 있다.

```text
동일한 문서 표본·질문·모델 조건
              │
       ┌──────┴──────┐
       ▼             ▼
D의 실험용 후보    E의 통합 후보
       └──────┬──────┘
              ▼
      동일 평가 기준으로 비교
              ▼
   선택·결합 후 E의 통합 흐름에 반영
```

병렬 구현은 공식 역할 변경이 아니라 비교 실험으로 기록한다. 공정한 비교를 위해 최종 비교 전에는 입력 데이터, 질문 세트, 모델·생성 설정, 응답 형식과 평가 기준을 같게 맞춘다. 두 후보의 인터페이스가 다르면 공통 입력·출력 형태로 변환하는 Adapter를 사용한 뒤 비교한다.

## 5. D의 비책임 범위

다음 업무는 D의 단독 책임으로 두지 않는다.

| 업무 | 주 담당 | D의 참여 범위 |
| :--- | :---: | :--- |
| 원문 수집·이용조건·Document Card | B | 학습 데이터에 필요한 필드 의견 제공 |
| 청킹·임베딩·Vector DB | C | 생성 입력에 필요한 검색 결과 형식 협의 |
| Hit@k·MRR 등 검색 성능 평가 | C | 검색 실패와 생성 실패 구분에 참여 |
| 운영·통합용 RAG Chain·검색 재시도·근거 충분성 판정 | E | 생성 컴포넌트 연결, 보류 표현 협의 및 실험용 Chain 후보 구현 가능 |
| 프롬프트 인젝션·비밀정보 등 통합 안전장치 | E | 학습 예시와 생성 Prompt 측면에서 지원 |
| Streamlit·UX·배포 | F | 응답 필드와 수준 선택값 협의 |
| 프로젝트 범위·비용·최종 모델 채택 결정 | A·팀 전체 | 실험 결과와 권고안 제공 |

D가 Fine-tuning 모델을 만들었다는 이유만으로 최종 서비스에 적용하지 않는다. 최종 채택은 팀의 통합 평가와 비용·일정 검토를 거쳐 결정한다.

## 6. 팀원과 반드시 협업하거나 논의할 사항

### 6.1. C와 협의

- Retriever가 D에게 전달할 값과 자료형
- 각 검색 문서의 `document_id`, 제목, 본문, URL 등 메타데이터
- 검색 결과가 없거나 일부 필드가 비어 있을 때의 처리 방식
- 검색 실패와 생성 실패를 구분하는 기록 방법

**논의 시점:** 2단계 생성 입출력 계약 승인 전

### 6.2. E와 협의

- D의 생성 컴포넌트를 전체 RAG Chain에 연결하는 방법
- 각자 구현한 RAG Chain 후보에서 의도적으로 다르게 둔 조건
- 두 후보를 비교할 때 같게 고정할 문서·질문·모델 설정·평가 기준
- 근거 충분성 판단을 생성 전과 생성 후 중 어디에서 수행할지
- 답변 보류 상태와 보류 사유의 표현
- D의 수준별 표현 평가와 E의 Faithfulness·인용·통합 평가 경계
- Prompt 인젝션 등 안전장치가 Prompt 및 학습 예시에 미치는 영향

**논의 시점:** 각 후보의 독립 구현을 시작하기 위한 사전 합의는 필수가 아니다. 다만 2단계 응답 스키마 확정 전에는 연동 필드를, 5단계 평가 계획 확정 전에는 비교 조건을 함께 확인한다.

### 6.3. F와 협의

- 설명 수준 선택값과 기본값
- UI에서 반드시 필요한 응답 필드
- 출처, 관련 항목, 답변 보류 상태의 화면 표시 방법
- Mock 응답과 실제 응답이 같은 구조를 사용하도록 하는 방법

**논의 시점:** 2단계 응답 스키마 승인 전

### 6.4. B와 협의

- 원문과 학습 예제에서 사용할 수 있는 필드
- 문서 저장·가공·외부 모델 전송 가능 범위
- 학습 데이터에 출처 원문을 어느 범위까지 포함할 수 있는지
- 실제 자료에서 확인할 수 없는 값을 임의 생성하지 않는 기준

**논의 시점:** 4단계 학습 데이터 명세 승인 전

### 6.5. A 및 팀 전체와 협의

- 팀 회의에서 정한 D·E 주 담당을 유지하고 병렬 후보 구현을 비교 실험으로 취급하는 원칙
- `쉽게`, `일반`, `깊이 있게`의 표현 기준
- 사용할 Baseline 모델과 Fine-tuning 가능 모델
- 외부 API 사용, 학습 비용과 실행 환경
- Fine-tuning 채택 기준과 결과 발표 방식

**논의 시점:** 역할 범위 승인 전 또는 각 관련 단계 승인 전

## 7. 최소 표본 전후의 업무 경계

### 최소 표본 전 가능

- 역할과 목표 행동 정의
- 입출력 계약 및 응답 스키마 설계
- Prompt Baseline 초안 작성
- 학습 데이터 스키마와 품질 기준 설계
- 평가 기준과 비교표 설계
- Mock Context 기반 생성 코드 작성
- 데이터 검증 및 학습 실행 코드 골격 작성

### 최소 표본 후 가능

- 실제 Prompt Baseline 측정
- 실제 문서 근거를 사용한 학습 예제 작성·검수
- Train·Validation·Test 데이터 분리
- Fine-tuning 실행
- 동일 평가 세트의 전후 비교
- 최종 모델 채택 또는 미채택 판단

## 8. 단계 완료 기준

다음 항목이 승인되면 Track B 팀원 D의 역할 범위가 확정된 것으로 본다.

- D가 개선하려는 목표 행동
- D의 직접 책임과 비책임 범위
- 초안의 Prompt·응답 스키마·RAG Chain 반영 방식
- B·C·E·F·A와 논의해야 할 항목과 시점
- Fine-tuning 결과가 좋지 않을 경우 미채택도 유효한 산출물이라는 원칙

승인 전에는 응답 스키마 설계나 Prompt 작성 등 다음 단계로 넘어가지 않는다.
