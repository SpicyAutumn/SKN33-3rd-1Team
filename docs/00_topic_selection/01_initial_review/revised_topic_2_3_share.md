# 3차 단위 프로젝트 변경 주제 검토안

> **문서 목적**  
> 기존 세 가지 아이디어를 교육 프로젝트에서 구현 가능한 수준으로 재정의하고, 팀 회의에서 주제 선정·범위 확정·데이터 확보 가능성을 검토하기 위한 공유 문서입니다.
>
> **기록 성격**  
> 이 문서는 팀원 개인이 제시한 2026-08-26 오전 원안을 같은 개인이 팀 회의 전에 구체화한 기획안입니다. 오전 원안과 본 구체화안은 하나의 연속된 개인 기획 기록이며, 팀의 합의·결정 또는 최종 추천 결과가 아닙니다.
>
> **변경 주제**
>
> 1. **1번 주제:** 지역박물관 연계 AI 역사교육 콘텐츠 제작·학습진단 플랫폼
> 2. **2번 주제:** 문화유산 굿즈 기획 및 디자인 의사결정 지원 시스템
> 3. **3번 주제:** 특정 시설·장소 방문자를 위한 주차장·대중교통·관람정보 통합 방문·여행 계획 도우미
>
> 아래 내용은 세부 주제 확정 전 검토안입니다. 대상 기관, 핵심 사용자, 데이터 범위, 구현 기능은 팀 회의 및 데이터 사전 조사 결과에 따라 보완해야 합니다.

## 전체 방향 요약

세 주제 모두 기존 아이디어의 장점을 유지하면서 프로젝트 범위를 현실적으로 구체화한 형태입니다.

| 구분 | 기존 접근 | 변경 접근 | 변경 효과 |
|---|---|---|---|
| 역사교육 | 초·중등 교과과정과 한국사 시험을 포괄하는 교육 프로그램 | 중학생 한국사 초심자를 위한 콘텐츠 제작·검수와 학습진단 | 사용자·교육범위·평가기준 명확화 |
| 문화유산 굿즈 | 재료 수급부터 디자인·제조까지 연계 | 굿즈 콘셉트와 디자인 방향의 의사결정 지원 | 제조업체·원가·재고 데이터 의존 감소 |
| 길 안내 | 기존 내비게이션을 발전시킨 종합 경로 안내 | 특정 시설 방문 전 교통·주차·관람 계획 제공 | 전국 실시간 교통·경로 계산 부담 감소 |

공통적으로 다음 원칙을 적용합니다.

- LLM이 사실이나 수치를 임의로 만들지 않도록 **공식 데이터와 출처를 우선**합니다.
- 설명문은 RAG·벡터DB로 검색하되, 가격·시간·거리 등 정확한 값은 관계형 DB나 API로 처리합니다.
- AI는 최종 결정을 대신하지 않고 **후보 비교, 근거 설명, 계획 초안 작성**을 지원합니다.
- 초기에는 기관 또는 장소 한 곳을 대상으로 검증한 뒤 확장합니다.
- Fine-tuning은 처음부터 필수로 적용하지 않고, RAG·프롬프트·평가 결과를 확인한 뒤 필요성을 판단합니다.

# 페이지 1/7 — 1번 주제: 서비스 개요와 핵심 기능

## 1. 주제명

### 지역박물관 연계 AI 역사교육 콘텐츠 제작·학습진단 플랫폼

## 2. 한 문장 정의

> 박물관·교사가 공식 유물 및 역사 자료를 바탕으로 교육 콘텐츠를 제작·검수하고, 중학생 한국사 초심자는 자신의 수준에 맞는 유물 해설·학습문제·오답 진단을 제공받는 RAG 기반 B2B2C 교육 플랫폼

## 3. 해결하려는 문제

박물관 교육 담당자와 교사는 신뢰할 수 있는 유물·역사 자료를 찾아 학습목표에 맞게 다시 구성해야 합니다. 학습자는 일반 검색이나 생성형 AI에서 자신의 수준에 맞는 설명을 얻을 수 있지만, 답변의 근거와 정확성을 직접 판단하기 어렵습니다.

이 시스템은 기존 문화유산 도슨트를 폐기하지 않고 다음과 같이 확장합니다.

```text
기존
일반 관람객이 문화유산에 질문하는 AI 도슨트

확장
박물관·교사가 공식 자료로 교육 콘텐츠를 제작·검수
        ↓
중학생이 수준별 유물 해설과 문제를 학습
        ↓
오답 원인과 취약 개념을 진단
        ↓
관련 유물·역사 자료를 이용해 보충학습
```

## 4. 핵심 사용자와 서비스 구조

### B2B 핵심 사용자

- 지방박물관 교육 담당자
- 중학교 역사 교사

### B2C 핵심 사용자

- 중학생 한국사 초심자

### 확장 사용자

- 한국사능력검정시험 기본 학습자
- 가족 단위 박물관 관람객
- 방과후 교육기관과 에듀테크 기업

```text
박물관·교사
   ↓ 콘텐츠 생성·근거 확인·수정·승인
AI 역사교육 콘텐츠 플랫폼
   ↓ 수준별 해설·문제·오답 진단
중학생 한국사 초심자
```

비용을 지불하거나 도입을 결정하는 기관과 실제 학습자가 구분되므로 B2B2C 서비스로 설명할 수 있습니다. MVP에서는 핵심 학습자를 중학생으로 고정하고, 한국사능력검정시험은 핵심 서비스가 아닌 평가·확장 자료로 사용합니다.

## 5. 핵심 기능

### 5.1 교사·박물관 담당자 기능

- 학년·시대·학습목표 선택
- 공식 자료 기반 수업자료 초안 생성
- 수준별 유물 해설과 활동지 생성
- 퀴즈·정답·해설 초안 생성
- 생성 문장의 근거와 출처 확인
- 근거 없는 문장과 과도한 단순화 표시
- 담당자 수정·승인 후 학습자에게 제공

### 5.2 학습자 기능

- 중학생 수준의 유물·역사 해설
- 유물과 시대·인물·사건 연결
- 문제풀이와 정답 근거 확인
- 정답과 오답 선지의 근거 비교
- 오답의 시대·주제·개념 분류
- 취약 개념 보충 설명과 후속 문제
- 공식 출처와 추가 학습자료 확인

### 5.3 단순 문제풀이 챗봇과의 차별점

```text
단순 챗봇
문제 입력 → 정답 제공 → 간단한 해설

권장 서비스
학습목표 설정 → 공식 자료 검색 → 콘텐츠 생성·검수
→ 학습자 문제풀이 → 오답·취약 개념 진단 → 근거 기반 보충학습
```

핵심 차별점은 **담당자의 교육 콘텐츠 제작·검수**와 **학습자의 오답 원인·취약 개념 진단**입니다.

# 페이지 2/7 — 1번 주제: 데이터·구현·제한요소와 권장 MVP

## 1. 필요한 데이터

| 데이터 종류 | 주요 내용 | 출처 후보 |
|---|---|---|
| 문화유산 데이터 | 유물명, 시대, 재질, 설명, 이미지 | e뮤지엄·박물관 공식 자료 |
| 역사 설명 데이터 | 시대·사건·인물·사료 해설 | 우리역사넷·한국사데이터베이스 |
| 교육과정 데이터 | 학습목표·성취기준·수준 | NCIC 국가교육과정 정보센터 |
| 문제 데이터 | 문제·정답·선지·관련 주제 | 한국사능력검정시험 공식 자료 |
| 검수 데이터 | 승인 여부, 수정 내용, 근거 일치 여부 | 교사·담당자 또는 팀 검수 |
| 학습 결과 | 정답 여부, 취약 개념, 후속 학습 결과 | 서비스 이용 과정에서 생성 |

활용 가능한 공식 후보는 다음과 같습니다.

- [e뮤지엄](https://emuseum.go.kr/index.html): 전국 박물관 소장품 검색·분류·Open API
- [우리역사넷](https://contents.history.go.kr/front/about/intro.do): 초등역사, 교과서 용어, 사료 해설, 한국사 이미지 등 교육 콘텐츠
- [한국사데이터베이스](https://db.history.go.kr/): 시대별 사료·연표·학술자료
- [NCIC 국가교육과정 정보센터](https://ncic.go.kr/board/B0024.cs): 2022 개정 교육과정 성취수준 자료
- [한국사능력검정시험 요강](https://www.historyexam.go.kr/pageLink.do?link=examGuideline) 및 [공식 기출문제 풀이](https://tok.historyexam.go.kr/)

교과과정 연계를 표시하려면 단순히 `교과서에 등장하는 내용`이라고 표현하지 않고, 해당 콘텐츠가 어떤 역사과 성취기준과 연결되는지 메타데이터로 관리해야 합니다.

## 2. 데이터 수집 및 전처리 방법

1. 지방 국립박물관 1곳과 하나의 시대·주제를 선정합니다.
2. 해당 주제와 연결되는 역사과 성취기준 1~2개를 선택합니다.
3. 대표 유물 30~50점의 공식 설명과 메타데이터를 수집합니다.
4. 우리역사넷·한국사데이터베이스에서 관련 역사 해설과 사료를 수집합니다.
5. 유물·개념·시대·성취기준의 연결표를 작성합니다.
6. 시험문제는 최근 일부 회차만 표본으로 사용하고 정답·개념 태그를 검수합니다.
7. 이미지·지도·삽화의 권리를 텍스트 데이터와 별도로 확인합니다.
8. 담당자가 검토한 설명·문제·평가기준만 서비스 데이터로 사용합니다.

### 권장 메타데이터

```text
content_id
content_type        # 유물, 역사해설, 사료, 문제
period              # 시대
topic               # 정치, 문화, 사회 등
achievement_code    # 성취기준
difficulty          # 중학생 초심자 기준 난도
source_name
source_url
license_type
review_status
reviewed_at
```

## 3. 권장 시스템 구조

```text
학습목표 또는 학습자 질문·오답
              ↓
      질문 유형·개념 분류
              ↓
 공식 유물·역사·교육과정 Hybrid RAG
              ↓
 수준별 해설·문제·오답 진단 생성
              ↓
 근거 일치·출처·난도·정답 유일성 검사
       ┌──────┴──────┐
     통과          근거 부족
       ↓               ↓
 담당자 검토       재검색 또는 답변 보류
       ↓
 학습자 제공·후속 학습
```

- **벡터DB·RAG:** 유물 설명, 역사 해설, 사료, 교육자료 검색
- **관계형 DB:** 문제·정답·성취기준·승인상태·학습결과 관리
- **LangGraph:** 분류 → 검색 → 생성 → 검증 → 재검색·보류 흐름
- **프롬프트:** 중학생 수준, 근거 표시, 추측 금지, 출력 형식 통제
- **Fine-tuning:** 기본 LLM·RAG·RAG+검증을 비교한 뒤 반복되는 분류·표현 문제가 확인될 때 검토

## 4. 주요 제한요소와 개선안

| 제한요소 | 발생 가능 문제 | 개선·권장안 |
|---|---|---|
| 교육범위 과다 | 초·중·고와 시험을 모두 다루면 수준 기준이 불명확 | 중학생과 성취기준 1~2개로 제한 |
| 역사적 과도한 단순화 | 쉬운 설명 과정에서 의미가 왜곡될 수 있음 | 원문 근거 비교와 담당자 승인 |
| 기출문제 저작권 | 사진·지도·삽화 권리가 다를 수 있음 | 텍스트·메타데이터와 이미지 권리 분리 관리 |
| 생성 문제 오류 | 정답이 없거나 여러 개인 문제가 생성될 수 있음 | 정답 유일성 검사와 승인 전 비공개 |
| 오답 원인 단정 | 실제 학습자의 사고과정을 잘못 판단할 수 있음 | `가능성이 높은 취약 개념`으로 표현하고 재질문 |
| 미성년자 정보 | 학습 이력과 개인정보가 결합될 수 있음 | 익명 ID와 최소 데이터만 저장 |
| 학습효과 과장 | 만족도가 실제 학습성과를 보장하지 않음 | 사전·사후 문제 또는 동일 개념 재평가 |

## 5. 권장 MVP

> **지방 국립박물관 한 곳과 중학교 역사 학습 주제 하나를 대상으로 담당자용 교육 콘텐츠 제작·검수와 학생용 수준별 해설·오답 진단을 제공하는 시스템**

| 항목 | 권장 범위 |
|---|---|
| 대상 기관 | 지방 국립박물관 1곳 |
| 유물 범위 | 하나의 시대·주제에 해당하는 30~50점 |
| 학습 범위 | 중학교 역사 성취기준 1~2개 |
| 핵심 학습자 | 중학생 한국사 초심자 |
| B2B 사용자 | 박물관 교육 담당자 또는 역사 교사 |
| 학습 콘텐츠 | 해설, 퀴즈, 오답 설명, 후속 학습 |
| 담당자 기능 | 생성, 근거 확인, 수정, 승인 |
| 시험 데이터 | 핵심 콘텐츠가 아닌 평가·확장 자료 |

### 평가 지표

- Retrieval Recall@K 또는 검색 적합성
- 정답 정확도와 정답 유일성
- 검색 근거와 생성 문장의 일치율
- 근거 없는 문장 비율
- 중학생 수준의 표현 적합성
- 오답 개념 분류 정확도
- 기본 LLM → RAG → RAG+검증의 개선 정도
- 응답시간과 호출 비용

# 페이지 3/7 — 2번 주제: 서비스 개요와 핵심 기능

## 1. 주제명

### 문화유산 굿즈 기획 및 디자인 의사결정 지원 시스템

## 2. 한 문장 정의

> 박물관·문화기관의 소장품 및 국가유산 데이터를 기반으로 유물의 역사적 의미와 시각적 특징을 분석하고, 타깃 고객·상품 유형·가격대·제작조건에 맞는 굿즈 콘셉트와 디자인 방향을 제안하는 AI 의사결정 지원 시스템

## 3. 해결하려는 문제

문화유산 굿즈를 기획할 때에는 유물의 역사적 의미, 문양과 색상, 고객 선호, 상품 형태, 제작 가능성, 저작권 등을 함께 검토해야 합니다. 그러나 관련 자료가 여러 기관과 문서에 분산되어 있고, 문화유산 전문가·디자이너·제조업체의 관점도 서로 다릅니다.

이 시스템은 여러 정보를 한 번에 검색하고 다음과 같은 의사결정을 지원합니다.

- 어떤 유물이 특정 상품에 적합한가?
- 유물의 어떤 형태·색상·문양을 활용할 수 있는가?
- 대상 고객에게 어떤 콘셉트가 적합한가?
- 후보 기획안의 장점·위험·차이는 무엇인가?
- 역사적 의미가 왜곡되거나 권리 문제가 발생할 가능성은 없는가?

## 4. 핵심 사용자

### 우선 사용자: B2B

- 박물관 및 문화기관의 문화상품 담당자
- 지역문화재단·관광재단의 상품기획 담당자
- 디자인 스튜디오와 지역 공방
- 지역축제·관광상품 담당자

### 확장 사용자: B2C

- 문화유산 기반 창작물을 기획하는 일반인·학생
- 기획안 선호도 조사에 참여하는 관람객
- 출시 예정 상품의 콘셉트를 비교하는 소비자

초기에는 **박물관 문화상품 기획 담당자 한 그룹**을 핵심 사용자로 두는 것이 좋습니다. 일반 소비자는 서비스의 직접 고객이라기보다 기획안에 대한 선호 데이터를 제공하는 참여자로 제한할 수 있습니다.

## 5. 핵심 사용 흐름

```text
유물 선택
  ↓
공식 역사·시대·재료·문양 정보 검색
  ↓
상품 종류·고객·가격대·제작조건 입력
  ↓
굿즈 콘셉트 후보 2~3건 생성
  ↓
문화적 적합성·타깃 적합성·제작성·권리 위험 비교
  ↓
담당자가 수정·보류·승인
```

## 6. 핵심 기능

### 6.1 문화유산 검색 및 분석

- 기관·시대·재질·용도·문양별 유물 검색
- 공식 유물 설명과 출처 제공
- 형태·색상·문양·상징성 태그 표시
- 유사하거나 함께 활용할 수 있는 유물 추천

### 6.2 굿즈 콘셉트 생성

사용자가 대상 유물, 상품 종류, 구매층, 가격대, 재료, 전통성·현대성 비율 등을 입력하면 다음 내용을 포함한 기획안을 생성합니다.

- 콘셉트명과 핵심 메시지
- 활용할 유물 요소와 활용 이유
- 권장 색상·문양·형태
- 대상 고객과 사용 상황
- 적용 가능한 상품군
- 제작 시 주의사항
- 사실 근거와 원문 출처

### 6.3 후보 비교와 평가

| 평가 기준 | 확인 내용 |
|---|---|
| 문화적 적합성 | 유물의 의미를 왜곡하지 않았는가? |
| 디자인 연관성 | 유물 요소가 상품에 자연스럽게 반영되는가? |
| 타깃 적합성 | 고객의 연령·용도·가격대에 맞는가? |
| 제작 가능성 | 재료와 가공 방식으로 구현 가능한가? |
| 차별성 | 기존 상품과 구분되는가? |
| 설명 가능성 | 제안 이유와 근거를 확인할 수 있는가? |
| 권리 위험 | 이미지·명칭·문양의 이용조건을 확인했는가? |

AI의 점수는 최종 판단이 아니라 **후보를 비교하기 위한 참고지표**로 사용합니다.

# 페이지 4/7 — 2번 주제: 데이터·구현·제한요소와 권장 MVP

## 1. 필요한 데이터

### 1.1 문화유산 사실 데이터

| 분류 | 주요 필드 |
|---|---|
| 기본정보 | 유물 ID, 유물명, 소장기관, 시대, 분류 |
| 특성정보 | 재질, 크기, 형태, 색상, 문양, 용도 |
| 설명정보 | 공식 해설, 역사적 의미, 관련 인물·사건 |
| 출처정보 | 원문 URL, 제공기관, 수집일, 데이터 기준일 |
| 권리정보 | 저작권자, 공공누리 유형, 상업 이용·변형 가능 여부 |

활용 가능한 공식 후보는 다음과 같습니다.

- [e뮤지엄](https://emuseum.go.kr/index.html): 전국 박물관 소장품 검색, 분류 및 Open API
- [국립중앙박물관 유물정보 API](https://www.data.go.kr/data/15121515/openapi.do): 유물명·시대·재질·주제어 등의 정형정보
- [국가유산청 국가유산포털](https://www.heritage.go.kr/): 국가유산 설명·이미지·일부 3D 자료
- 대상 지방박물관 공식 홈페이지, 전시 해설, 공개 도록

### 1.2 디자인·제작조건 데이터

- 유물에서 추출한 색상·문양·형태·상징성 태그
- 상품 종류, 크기, 재료, 인쇄·가공 방식
- 표현 가능한 색상 수와 세부 문양 수준
- 최소 주문량, 예상 가격대, 제작 기간
- 문화적·종교적 표현 주의사항

공공데이터만으로는 실제 제작 가능성을 판단하기 어렵습니다. 협력업체 정보가 없다면 팀이 정의한 값을 **교육용 가상 제작조건**으로 명시하고, 실제 견적처럼 표현하지 않아야 합니다.

### 1.3 소비자 선호 데이터

간단한 설문을 통해 기획안별 구매 의향, 디자인 선호도, 유물 연관성, 적정 가격대와 개선 의견을 수집할 수 있습니다. 소규모 설문 결과는 전체 시장을 대표하는 통계가 아니라 **후보 비교를 위한 파일럿 자료**로 정의합니다.

## 2. 데이터 수집 및 전처리 방법

1. 대상 박물관 1곳과 대표 유물 30~50점을 선정합니다.
2. API·CSV·공식 홈페이지에서 원본 데이터를 수집합니다.
3. 원본 데이터는 수정하지 않고 별도 보관합니다.
4. 유물명·시대·재질·문양 표현을 통일합니다.
5. 중복 자료와 출처가 불명확한 문장을 제거합니다.
6. LLM이 추출한 디자인 태그는 담당자가 검토합니다.
7. 출처 URL·수집일·이용조건을 유물 데이터와 함께 저장합니다.
8. 검토 완료 데이터만 벡터DB에 등록합니다.

온라인 쇼핑몰 리뷰·SNS 게시물을 무단으로 대량 수집하는 방식은 이용약관·저작권·개인정보 문제가 있으므로 권장하지 않습니다. 필요한 선호정보는 자체 익명 설문이나 공개 이용이 허용된 데이터로 확보합니다.

## 3. 권장 시스템 구조

```text
사용자 기획 조건
        ↓
LangGraph 기획 워크플로
 ┌────────────┬────────────┬────────────┐
 문화유산 RAG   제작조건 DB    디자인·권리 규칙
 └────────────┴────────────┴────────────┘
        ↓
기획안 후보 생성
        ↓
사실·제약조건·문화적 적합성 검사
        ↓
비교표 + 근거 출처 + 주의사항
        ↓
담당자 검토·수정·승인
```

- **벡터DB·RAG:** 공식 유물 설명, 전시 해설, 디자인 지침 검색
- **관계형 DB:** 크기·가격·제작기간·가공조건처럼 정확한 값 관리
- **LangGraph:** 검색 → 후보 생성 → 조건 검사 → 비교평가의 단계 관리
- **프롬프트:** 출력 형식, 근거 표시, 금지 표현 통제
- **Fine-tuning:** 검토 완료된 기획안이 충분히 쌓인 이후 문체·형식 일관화가 필요할 때 검토

## 4. 주요 제한요소와 개선안

| 제한요소 | 발생 가능 문제 | 개선·권장안 |
|---|---|---|
| 이미지 저작권 | 상업 이용 또는 변형이 제한될 수 있음 | 항목별 이용조건 저장, 출처표시, 미확인 이미지는 결과에서 제외 |
| 문화적 왜곡 | 상징이나 용도를 잘못 해석할 수 있음 | 공식 해설만 사실 근거로 사용, 민감 항목은 담당자 승인 필수 |
| 제조정보 부족 | AI가 구현하기 어려운 디자인을 제안할 수 있음 | 상품군을 제한하고 가상 조건임을 표시, 제작조건 규칙 검사 |
| 시장성 과장 | 소규모 설문을 시장 수요로 오해할 수 있음 | 파일럿 선호도와 실제 판매 데이터를 명확히 구분 |
| 이미지 생성 의존 | 결과가 화려하지만 RAG 검증이 약해질 수 있음 | 이미지 생성은 선택 기능으로 두고 근거·비교 기능을 핵심으로 설정 |

## 5. 권장 MVP

> **지방 국립박물관 1곳의 대표 유물 30~50점을 활용하여 박물관 상품기획 담당자에게 문구·패브릭·생활소품 기획안과 비교평가를 제공하는 시스템**

- 상품군 3개 이내
- 사용자 유형 1개: 문화상품 기획 담당자
- 기획안 후보 2~3건 생성
- 공식 출처와 권리정보 표시
- 담당자 수정·승인 기능
- 소규모 소비자 선호도 조사
- 이미지 생성은 선택 기능

### 평가 지표

- 근거 출처가 포함된 답변 비율
- 검색된 근거와 생성 내용의 일치율
- 필수 제작조건 준수율
- 담당자의 문화적 적합성 평가
- 기획안 수정 횟수와 만족도

# 페이지 5/7 — 3번 주제: 서비스 개요와 핵심 기능

## 1. 주제명

### 특정 시설·장소 방문자를 위한 주차장·대중교통·관람정보 통합 방문·여행 계획 도우미

## 2. 한 문장 정의

> 특정 박물관·미술관·공연장·관광시설 방문자의 방문 일시, 이동수단, 관람시간, 동행자 조건을 분석하여 주차장·대중교통·시설 이용정보·주변 관광정보를 결합한 방문 계획을 제공하는 AI 도우미

## 3. 해결하려는 문제

시설 방문자는 지도에서 경로를 찾는 것 외에도 운영시간, 휴관일, 주차요금, 대중교통, 입장 마감, 편의시설, 관람 소요시간과 주변 일정을 각각 확인해야 합니다. 특히 유아·노약자·장애인 동반 여부나 날씨에 따라 적합한 계획이 달라집니다.

이 시스템은 내비게이션을 대체하지 않고 다음 질문에 답하는 것을 목표로 합니다.

- 방문일에 정상 운영하는가?
- 자동차와 대중교통 중 어떤 방법이 조건에 적합한가?
- 어떤 주차장이 거리·요금·운영시간 측면에서 유리한가?
- 1시간 또는 2시간 동안 무엇을 관람할 수 있는가?
- 비·폭염·한파가 있을 때 계획을 어떻게 조정해야 하는가?
- 관람 후 방문할 수 있는 주변 장소는 어디인가?

## 4. 핵심 사용자

- 자가용 또는 대중교통으로 방문하는 일반 관람객
- 유아·노약자를 동반한 가족 관람객
- 제한된 시간에 핵심 시설을 보려는 여행객
- 무장애·편의시설 정보가 필요한 방문객

초기에는 **자가용 또는 대중교통으로 지방 박물관을 방문하는 가족 관람객**처럼 한 그룹을 선택하는 것이 좋습니다.

## 5. 사용자 입력정보

- 방문할 시설
- 방문 예정일과 도착 희망시간
- 출발지 또는 출발 지역
- 이동수단: 자동차·대중교통
- 전체 이용 가능시간
- 동행자: 유아·노약자·휠체어 이용자 등
- 주차요금·도보거리·환승 횟수 우선순위
- 식사·주변 관광 등 추가 희망사항

개인화를 위해 직업이나 상세 연령을 필수로 받을 필요는 없습니다. 방문 계획에 직접 필요한 조건만 질문하여 접근성과 개인정보 부담을 줄입니다.

## 6. 핵심 기능

### 6.1 방문 가능 여부 확인

- 휴관일과 운영시간 확인
- 입장 마감시간과 예상 도착시간 비교
- 행사·공사·임시휴관 공지 검색
- 계획이 불가능할 경우 대체 일시 제안

# 페이지 6/7 — 3번 주제: 데이터·구현·제한요소와 권장 MVP

## 1. 데이터 유형별 처리 원칙

이 주제에서는 모든 데이터를 벡터DB에 저장하면 안 됩니다.

| 데이터 종류 | 예시 | 권장 처리 방식 |
|---|---|---|
| 문서형 정보 | 관람 안내, 휴관 규정, 편의시설 설명 | 벡터DB·RAG |
| 정형 데이터 | 운영시간, 요금, 주차면 수 | 관계형 DB |
| 공간 데이터 | 주소, 위도·경도, 거리 | 공간 계산·지도 API |
| 실시간 데이터 | 버스 도착, 날씨, 주차 잔여면 | 호출 시점의 외부 API |
| 추천 규칙 | 입장 마감, 우천, 이동시간 조건 | 규칙 엔진·프로그램 로직 |

예를 들어 주차장 설명은 RAG로 검색할 수 있지만, 현재 잔여면은 실시간 API가 제공하는 값만 사용해야 합니다. 오래된 값을 임베딩하여 현재 정보처럼 답하면 안 됩니다.

## 2. 데이터와 공식 출처 후보

| 데이터 | 주요 내용 | 출처 후보 |
|---|---|---|
| 시설 | 운영시간, 휴관일, 요금, 편의시설, 공지 | 대상 시설 공식 홈페이지 |
| 주차장 | 위치, 주차면, 운영시간, 요금 | [전국주차장정보 표준데이터](https://www.data.go.kr/data/15012896/openapi.do), 지자체 API |
| 대중교통 | 정류장, 노선, 버스 도착예정시간 | [국토교통부 TAGO 버스도착정보](https://www.data.go.kr/data/15098530/openapi.do) |
| 관광정보 | 주변 관광지·문화시설·행사 | 한국관광공사 TourAPI, 지자체 관광데이터 |
| 기상 | 시간별 날씨, 강수, 기온 | [기상청 단기예보](https://www.data.go.kr/dataset/15000099/openapi.do?lang=ko) |
| 지도 | 좌표 변환, 마커, 외부 길찾기 | [네이버 지도 API](https://navermaps.github.io/maps.js.ncp/docs/) 또는 다른 지도 플랫폼 |

전국 주차장 표준데이터는 시설·요금 정보로 활용할 수 있지만 실시간 빈자리 데이터로 간주하면 안 됩니다. TAGO·TourAPI도 대상 지역 지원 여부, 호출한도, 서비스 변경 공지를 개발 전에 실제 호출로 확인해야 합니다.

## 3. 데이터 수집 및 관리 방법

1. 핵심 시설 1곳과 반경 3~5km를 범위로 설정합니다.
2. 주차장 5~20곳, 주요 정류장 5~10곳, 주변 장소 10~30곳을 수집합니다.
3. API 응답과 공식 문서 원본을 `raw` 데이터로 보존합니다.
4. 장소마다 내부 `place_id`를 부여하고 명칭·주소·좌표를 통일합니다.
5. 운영시간·요금의 단위와 누락값을 정리합니다.
6. 폐쇄·이전·휴관 정보를 수동 표본검사합니다.
7. 출처, 기준일, 마지막 검증일, 실시간 여부를 함께 저장합니다.
8. API 장애 시 사용할 대체정보와 안내문을 준비합니다.

### 출처 우선순위

```text
시설 공식 홈페이지
  → 공공기관 API
  → 지방자치단체 공개자료
  → 지도 플랫폼 정보
  → 사용자 제공 정보
```

## 4. 권장 시스템 구조

```text
방문일·이동수단·관람시간·동행자 조건
                    ↓
            LangGraph 계획 관리자
      ┌────────────┼────────────┐
    시설 RAG      정형·공간 DB     실시간 API
   관람·규정      거리·요금       날씨·버스·주차
      └────────────┼────────────┘
                    ↓
       필수조건 검사 + 후보 점수 계산
                    ↓
       일정 설명 + 대안 + 출처·조회시각
                    ↓
             외부 지도 길찾기 연결
```

LLM은 거리·요금·시간을 임의로 계산하지 않고, 프로그램이 계산한 결과를 자연어로 설명하는 역할을 맡습니다.

## 5. 주요 제한요소와 개선안

| 제한요소 | 발생 가능 문제 | 개선·권장안 |
|---|---|---|
| 실시간 주차정보 부족 | 실제 빈자리와 안내가 다를 수 있음 | 제공 지역만 실시간 표시, 그 외에는 총면수·운영정보와 미제공 안내 |
| API 장애·변경 | 시연 중 데이터 호출 실패 | 캐시·예제 데이터·대체 출처 준비, 마지막 조회시각 표시 |
| 데이터 시차 | 폐쇄·요금 변경이 늦게 반영될 수 있음 | 기준일과 검증일 표시, 핵심 장소 수동 점검 |
| 잘못된 경로 안내 | 안전 또는 일정 문제가 발생할 수 있음 | 자체 길안내 대신 외부 지도 연결, 추천과 실제 경로를 구분 |
| 과도한 범위 | 전국 데이터 정합성 검증이 어려움 | 시설 1곳·반경 3~5km·이동수단 2개로 제한 |
| 개인정보 과수집 | 출발지·동행자 정보 부담 | 정확한 주소 대신 역·동 단위 선택 허용, 세션 종료 후 삭제 |

### 교육과정 적합성·평가 가능성·B2B2C 균형을 우선한다면

**지역박물관 연계 AI 역사교육 콘텐츠 제작·학습진단 플랫폼**이 적합합니다.

- 공식 유물·역사·교육과정·시험자료를 연결할 수 있습니다.
- 검색, 답변, 출처, 정답, 오답 분류를 반복 평가하기 쉽습니다.
- 박물관·교사의 콘텐츠 제작 업무와 학생의 학습 경험을 함께 보여줄 수 있습니다.
- 기존 문화유산 도슨트 조사와 데이터 범위를 재사용할 수 있습니다.

다만 중학생과 성취기준 1~2개로 범위를 제한하고, 생성 문제와 설명은 담당자 승인 후 제공해야 합니다.

### 기획 직무와 문화상품 비즈니스를 강조한다면

**문화유산 굿즈 기획 및 디자인 의사결정 지원 시스템**이 적합합니다.

- 공식 자료를 중심으로 데이터 범위를 통제하기 쉽습니다.
- 외부 API 장애와 실시간 데이터 영향을 덜 받습니다.
- 유물의 의미와 제작조건을 연결하는 B2B 의사결정을 보여줄 수 있습니다.

다만 저작권과 문화적 왜곡을 관리하고, 제조 가능성과 시장성을 실제 사실처럼 과장하지 않아야 합니다.

### 사용자 체감과 복합 시스템 구성을 우선한다면

**특정 시설 방문·여행 계획 도우미**가 적합합니다.

- 사용자 조건에 따라 결과가 달라져 시연 효과가 좋습니다.
- RAG·정형DB·공간 데이터·외부 API·LangGraph를 종합적으로 보여줄 수 있습니다.
- 시설 운영기관을 B2B 고객, 방문객을 B2C 사용자로 설명하기 쉽습니다.

다만 전국 서비스와 자체 내비게이션을 목표로 하지 말고, 시설 한 곳과 제한된 지역에서 정확성을 검증해야 합니다.

## 4. 현재 단계의 추천 순위

### 1순위: 지역박물관 연계 AI 역사교육 콘텐츠 제작·학습진단 플랫폼

교육과정에서 학습한 RAG, 벡터DB, 프롬프트, LangChain·LangGraph와 환각 방지를 가장 자연스럽게 적용할 수 있습니다. 공식 자료와 평가문항을 이용한 정량·정성 평가가 가능하고, B2B 콘텐츠 제작과 B2C 학습 경험을 함께 설명할 수 있다는 점에서 최우선으로 추천합니다.

### 2순위: 문화유산 굿즈 기획 및 디자인 의사결정 지원 시스템

문화유산 데이터의 재사용과 B2B 기획 도구라는 차별성이 있습니다. 다만 이미지 권리와 제조조건 데이터가 부족할 경우 실제 제조 추천이 아니라 상품기획서·디자인 브리프 생성으로 범위를 유지해야 합니다.

### 3순위: 특정 시설 방문·여행 계획 도우미

포트폴리오와 시연 효과는 높지만 API 연동, 실시간 데이터, 공간 계산과 장애 대응까지 포함되어 개발 난도가 높습니다. 시설 한 곳과 이동수단 두 개로 제한할 수 있을 때 추진하는 것이 적절합니다.
