# Track C Streamlit 인계 — 문화유산 맞춤형 답변 서비스

작성일: 2026-08-31. 기획 대화 및 현재 로컬 코드를 확인해 작성했다. 이 문서는 팀 공통 API 계약을 변경하거나 새 담당자를 확정하는 문서가 아니다.

## 1. 지금 인계하는 것은 무엇인가

문화유산 RAG의 화면과 사용자 흐름을 먼저 만든 **Streamlit 시연용 앱**이다. 기존 코드를 이어서 개선해도 되고, 아래 사용자 요구를 유지하며 새로 구현해도 된다.

- 저장소: `SKN33-3rd-1Team`
- 작성 시점 브랜치: `feature/track-c-streamlit-mock`
- 작업 위치: 현재 체크아웃한 저장소 루트
- 문서 작성 중 마지막 확인 시 앱 파일은 Git 커밋 준비 영역에 올라가 있었고, 새 docs/track_c 문서는 미추적 상태였다. 커밋·푸시·PR 완료로 간주하지 말고 다시 확인할 것.
- 현재 앱은 질문 내용을 검색하지 않는다. 선택한 응답 유형의 고정 Mock 응답을 표시한다.
- 실제 Pinecone 검색, RAG 답변 생성, RAGAS 계산, LLM 심사 API 호출은 앱에 연결되지 않았다.
- 그래프 확장과 마지막 항목의 한 줄 설명 표시는 브라우저에서 실제 동작한다. 내용은 예시 데이터다.

## 2. 사용자 의도와 유지해야 할 화면

프로젝트의 핵심은 **문화유산 맞춤형 답변**이다. 어린이·청소년·일반인·전문가 등에 맞춰 말투, 용어, 설명 깊이를 바꾸는 것을 원한다. UI가 대상을 선택하고 전달하며, 생성 담당 코드가 실제 설명 수준을 적용해야 한다. 현재 대상 선택 UI도 아직 없다.

앱은 기본 실행 파일과 탭별 파일을 분리한다. 한 파일에 모든 화면과 검색 로직을 넣지 않는다. 현재 탭은 다음 네 개다. 사용자가 제거한 `서비스 안내` 탭은 임의로 복원하지 않는다.

| 탭 | 사용자가 원하는 동작 | 현재 상태 |
| --- | --- | --- |
| 질문하기 | 질문·설명 수준 입력, 답변, TTS, 출처·근거 표시 | Mock 질문 제출·유형별 화면·브라우저 TTS 코드 있음. 설명 수준 미구현 |
| 답변 과정 | 방금 질문의 실제 검색 청크·순위·점수·사용 근거·최종 답변 | 같은 세션 결과를 표시하나 입력 데이터는 Mock |
| 평가 결과 | 점수뿐 아니라 평가 기준·입력 자료·판정 이유를 확인 | RAGAS 4개 고정 예시 점수와 고정 심사 의견 |
| 문화유산 탐험 지도 | 노드를 클릭하면 그 노드에서 가지가 펼쳐짐. 마지막 노드는 한 줄 설명 | HTML/JS로 클릭·펼치기·접기·설명창 동작, 관계와 설명은 Mock |

### 질문하기

- 응답 유형: `answered`, `insufficient_evidence`, `needs_clarification`, `corrected_premise`, `safety_refusal`, `out_of_scope`.
- 추가 질문은 최대 1회, 선택지는 최대 3개 방향으로 논의했다. 현재 UI는 선택지만 3개로 자른다. 1회 제한의 상태 제어는 구현되지 않았다.
- 직접 입력과 다른 후보 찾기도 논의했다. 다른 후보 찾기 최대 2회는 아이디어이며, 현재 버튼은 기능이 없다.
- 잘못된 전제는 부드러운 `확인된 정보` 안내로 표시한다.
- TTS는 실제 출력 문장을 읽어야 한다. 현재 정상 답변·추가 질문·전제 정정에서만 버튼이 나온다.

### 답변 과정

사용자의 비유는 **투명한 생산라인**이다. 일반적인 RAG 구조 소개나 AI의 추측 설명이 아니라, 해당 요청에서 실제로 관찰한 처리 결과를 보여준다.

`질문 → 검색된 청크 전체 → 실제 사용된 chunk_id 강조 → 최종 답변·출처`

- 처음 검색됐지만 최종 사용되지 않은 청크도 구별해서 보여준다.
- 검색 점수는 `score_type`을 함께 확인한다. 유사도·거리·재정렬 점수를 모두 정확도처럼 표시하지 않는다.
- 모델의 숨은 사고과정, 비밀 프롬프트, API 키를 노출하는 화면이 아니다.
- 현재 전제 정정 화면은 `premise_correction.corrected_premise`를 출력하지만 과정·평가 탭은 `message`만 출력한다. 실제 사용자에게 보인 문장과 기록할 평가 대상 문장을 일치시켜야 한다.

### 평가 결과

다음 수업 자료를 참고한 UI 아이디어다. 노트북이나 실제 평가 실행 결과가 이 PR에 포함됐다는 의미는 아니다.

- `01_llm_eval.ipynb`: 평가 설계의 기본 개념.
- `02_Evaluation_LLM_lm-eval-harness.ipynb`: 모델 벤치마크 비교.
- `03_llm_as_a_judge_hf_cookbook.ipynb`: 정해진 평가 기준으로 심사 모델이 점수와 의견을 남기는 방식.
- `04_ragas.ipynb`: 검색 문맥·생성 답변·기준 답을 이용한 RAG 평가.
- 참고 노트북은 저장소에 포함되어 있지 않을 수 있다. 필요하면 팀의 수업 자료에서 위 파일명으로 찾아 별도 제공받는다.

| 지표 | 화면에서 설명할 내용 |
| --- | --- |
| Faithfulness | 답변의 주장들이 검색된 근거로 뒷받침되는가 |
| Answer Relevancy | 답변이 질문에 맞게 응답하는가 |
| Context Precision | 관련 근거를 상위에 잘 검색했는가 |
| Context Recall | 기준 답에 필요한 정보를 검색 문맥이 충분히 담고 있는가 |

사용자는 각 점수가 왜 나왔는지 보고 싶어 한다. 실서비스에서는 질문·검색 청크·최종 답변·기준 답(사용하는 지표에서 필요)·평가 기준·실제 점수·실제 심사 의견을 연결한다.

현재 `0.92 / 0.89 / 0.86 / 0.90`은 임의 예시 숫자다. 정확도나 실험 성과로 발표하면 안 된다. `통과`, `개선 필요 없음` 및 길쌈노래에 관한 심사 이유도 고정 문구다. 다른 질문이나 전제 정정 응답에도 같은 문구가 나타날 수 있다.

RAGAS 점수와 별도로 실행한 LLM 심사 의견은 구분해서 표시해야 한다. 별도 심사 모델의 의견이 RAGAS의 특정 소수점 점수를 정확히 설명한다고 주장하지 않는다. 심사 의견이 없으면 없다고 표시한다. LLM 심사는 사람의 검토를 대체하지 않는다.

기존 평가 CSV를 연결할 때 문장 유사성으로 임의 매칭하지 않는다. 요청 ID, 응답 버전, 문맥, 설명 수준 등을 맞춰야 한다. 질문이 바뀌면 이전 평가를 비우고, 평가가 없으면 `평가 전`으로 표시한다. 기준 답이 필요한 지표를 기준 답 없이 만든 숫자로 채우지 않는다. 탭 클릭마다 유료 평가 API가 재실행되지 않도록 별도 실행 버튼이나 미리 계산한 결과를 사용한다.

### 탐험 지도 — 가장 중요한 상호작용 요구

초기에는 파란 중심 노드 `길쌈노래`만 보인다.

1. **길쌈노래 자체 클릭** → 선으로 연결된 민요·노동요·길쌈이 펼쳐진다.
2. **민요 노드 자체 클릭** → 민요에서 아리랑·강강술래·정선아리랑 가지가 펼쳐진다.
3. 열린 노드를 다시 클릭하면 그 가지가 접힌다.
4. 마지막 항목인 아리랑 등을 클릭하면 지도 안의 작은 설명창에 짧은 한 문장이 뜬다.
5. 다른 마지막 항목을 클릭하면 설명이 바뀐다. 같은 항목 재클릭, 닫기 버튼 또는 Esc로 닫을 수 있다.
6. `처음으로`는 전체 가지와 설명을 초기화한다.

**중심 문화유산 아래에 별도 카드 목록을 나열하는 방식으로 돌아가면 안 된다.** 사용자가 여러 번 수정 요청한 부분이다. 클릭한 노드에서 직접 가지가 뻗는 지도가 핵심이다.

- 현재: 곡선 연결선, 파란 중심 노드, 연한 파란 중간 노드, 연한 초록 마지막 노드, 확장/접기 기호, 스크롤 가능한 캔버스.
- 미래: 실제 응답/메타데이터에서 연관 키워드를 받고, 클릭한 키워드로 관련 문서를 검색해 가지를 추가한다. 마지막 설명도 실제 원문에 근거해 가져온다.
- 현재 클릭은 브라우저에 전달된 Mock 자료를 펼칠 뿐 서버를 재호출하지 않는다. 함수 하나 교체만으로 비동기 재검색이 완성되는 구조는 아니다. 클라이언트 클릭 → Python/서버 검색 → 지도 데이터 갱신 연결이 추가로 필요하다.
- 과거 질문을 연결하는 지도도 원래 아이디어였다. 현재 질문 이력은 저장하지만 지도에서는 표시하지 않는다.
- 더 뻗을 자료가 없으면 빈 상태를 안내하고 임의의 관계나 설명을 만들지 않는다.

## 3. 파일 구성

경로는 저장소 루트 기준이다.

```text
app/
  app.py                         # 실행·페이지 설정·4개 탭 배치
  mock_responses.py              # 고정 응답·청크·출처·related_keywords 예시
  tabs/
    chat.py                      # 질문 제출·last_result·질문 기록
    process.py                   # 같은 요청의 검색/사용 청크 표시
    evaluation.py                # 고정 RAGAS 점수·고정 LLM 심사 의견
    explore.py                   # 지도에 전달할 데이터·예시 관계·한 줄 설명
    guide.py                     # 남아 있지만 현재 앱에서 사용하지 않음
  components/
    response_cards.py            # 응답 유형별 화면·브라우저 TTS
    citations.py                 # 출처·원문 링크·근거 문장
    exploration_map.html         # 클릭 확장 지도·설명창 HTML/CSS/JS
```

`explore.py`의 `MOCK_RELATED_SEARCH_RESULTS`는 관계 예시이고, `MOCK_TOPIC_SUMMARIES`는 한 줄 설명 예시다. HTML에는 JSON을 전달하며 표시 문자열은 `textContent`로 넣는다. 외부 데이터로 바꾸더라도 이스케이프와 스크립트 삽입 방지를 유지한다.

## 4. 탭 간 상태 공유

`st.session_state`로 동일 브라우저 세션의 데이터를 공유한다. 아래는 현재 UI 내부 구조이며 팀의 확정된 `ServiceResponse` 스키마가 아니다.

```python
last_result = {
    "question": "사용자가 제출한 질문",
    "response": {...},             # response_type, message, citations 등
    "retrieved_contexts": [...],   # 현재 요청의 검색 청크
    "used_chunk_ids": [...],       # 최종 답변에 사용한 청크 ID
    "related_keywords": [
        {"keyword": "민요", "relation": "유형"}
    ],
}
```

- `question_history`: 최근 10건의 질문·제목. 저장만 하며 현재 지도는 사용하지 않음.
- `pending_question`: 이전 카드 UI가 후속 질문을 입력칸에 넣기 위해 썼던 경로. 현재 지도는 이 값을 보내지 않음.
- `selected_clarification`, `clarification_input`: 선택·직접 입력의 임시 상태. 실제 추가 질의로 연결되지 않음.
- 평가 숫자와 심사 의견은 요청별 상태가 아니라 모듈 상수다. 실평가 연결 시 반드시 바꿔야 함.
- 지도에서 펼친 상태는 iframe JavaScript 안에만 있다. 탭 전환·앱 재실행 시 유지 여부를 점검하고 필요하면 명시적으로 저장해야 함.
- `session_state`는 영구 DB나 다른 PC에서 이어지는 저장 기능이 아니다. 새 세션·재접속에는 사라질 수 있다.
- `st.cache_data`를 사용자별 최근 질문 보관함으로 쓰지 않는다. 공유 캐시에 개인정보가 섞이지 않게 한다.
- 실연결 때 요청 ID를 두고 질문·문맥·답변·평가·설명 수준을 하나의 요청 기록으로 묶는다.

## 5. 팀 연동에서 확인해야 할 사항

### 계약과 현재 구현 사이의 차이

- 현재 `docs/track_b/02_generation_contract.md`는 `0.2.0-draft`이며 `RetrievedContext.source`와 `page`를 사용한다.
- 현재 검색 코드 `src/rag_indexing/pinecone_store.py`도 `source`=원문 URL, `page`를 반환한다.
- 팀 대화에서는 `source_url` 중심의 0.3 초안을 논의했다. 해당 논의가 main이나 다른 브랜치에 최종 반영됐는지는 확인해야 한다.
- 대화상 `Citation.source`는 화면 표시용 출처 이름으로 두고 URL과 분리하는 방향에 동의했다.
- 대화상 `RetrievedContext.source_url → Citation.url`로 연결하기로 논의했지만 **현재 UI는 citations[].source_url을 읽는다.** 그대로 붙이면 원문 링크가 안 나올 수 있다.
- 현재 출처 이름은 `mock_responses.SOURCE_NAME` 상수다. 실제 여러 기관이 들어오면 항목별 이름을 받아야 한다.
- `page`는 UI에서 사용하지 않는다.
- 별도의 evidence 필드보다는 같은 요청의 `used_chunk_ids`와 `RetrievedContext.content`를 연결해 근거를 표시하는 방향이었다. 현재 UI는 `citations[].content`를 출력한다.

### 역할 경계

- UI/Track C: 화면·상태·설명 수준 선택·응답 연결·통합 확인.
- 생성/RAG 담당: 설명 수준 적용, 실제 답변 생성, used_chunk_ids 유효성 검증, 검색 문맥에서 출처와 본문 조립.
- 검색 담당: Pinecone 검색 및 관련 문화유산 검색 데이터 제공.
- 기존 대화에서 검색 반환 Adapter와 테스트 수정은 Track C에서 맡겠다고 이야기했다. 완료한 것은 아니다. 검색 담당과 변경 파일·최종 계약을 맞춘다.
- 근거 표시를 위해 같은 청크를 Pinecone에서 다시 조회하지 않는다. **탐험 지도에서 새 키워드로 관련 자료를 검색하는 동작은 별도 검색**이므로 이 원칙과 다르다.

### 맞춤 답변

현재 생성 계약에는 `audience_level: easy/general/advanced`가 있다. 대화 중 언급한 `audience="child"`는 예시였고 확정 코드가 아니다. 어린이·청소년·일반·전문가라는 화면 이름과 계약 값의 대응을 생성 담당과 맞춘다. UI가 선택만 받고 실제 답변에는 적용하지 않는 상태를 완료로 표시하지 않는다. TTS와 평가도 선택한 설명 수준의 최종 답변을 기준으로 연결한다.

### Pinecone 참고

기존 문서와 팀 공유에 따르면 v1 전체 179,028개 청크가 `aks-rag-v1`, namespace `__default__`에 적재되어 있다. 모델은 `text-embedding-3-small`, 1,536차원, cosine이다. 이 인계 작업에서는 계정이나 현재 적재 상태를 재조회하지 않았다.

실행에 필요한 키는 보안 경로로 별도 전달받는다. `OPENAI_API_KEY`, `PINECONE_API_KEY`, `PINECONE_INDEX_NAME`, `PINECONE_NAMESPACE`를 문서·코드·PR에 값까지 넣지 않는다. 이 UI 작업을 이유로 전체 청크 재적재, namespace 삭제, 임베딩 재생성, 유료 플랜 변경을 수행하지 않는다.

## 6. 알려진 한계 — PR에서 숨기지 말 것

1. 임의 질문을 써도 정상 응답 유형이면 길쌈노래 예시가 나온다. 질문 이해나 키워드 자동 추출이 실제로 수행되는 게 아니다.
2. 평가 점수와 심사 이유는 고정 예시이며 답변 내용을 정확히 검증한 결과가 아니다. 실제 근거 없는 문장이 있어도 통과처럼 보일 수 있다.
3. Mock 전제 정정 사례의 제목은 경복궁이지만 document_id/URL은 길쌈노래 예시를 재사용한다. 사실 검증용 출처로 사용하면 안 된다. Mock ID 명명도 계약의 MOCK- 원칙과 맞춰야 한다.
4. TTS는 iframe에서 브라우저 SpeechSynthesis를 실행하는 방식이다. OS 한국어 음성, 브라우저의 사용자 동작/음성 정책에 영향을 받으며 모든 환경의 재생 성공을 검증하지 않았다. 전용 정지·속도·음성 선택 기능은 없다. 외부 입력을 JS에 삽입하기 전 `</script>` 등 이스케이프도 보강해야 한다.
5. 실행 환경에서 `st.components.v1.html` 사용 중단 예정 경고가 관찰됐다. JS가 실행되는 대체 컴포넌트 방식을 실제 설치 버전과 확인한다. 단순히 `st.html`로 바꾸면 동일하게 동작한다고 가정하지 않는다.
6. 답변 과정의 일부 문구는 Mock인데도 ‘실제’라고 표현한다. 예시와 실측 표시를 화면 전체에서 통일할 필요가 있다.
7. 참조 문맥이 있다고 해서 모두 검색 점수를 유사도로 단정하지 않는다. 현재 화면은 모든 숫자를 유사도로 출력한다.
8. 맞춤 대상 선택, 추가 질문 1회 제한, 다른 후보 찾기, 실제 오류/타임아웃 처리, 관련 주제에서 질문으로 이동, 과거 질문 지도는 미완성이다.

## 7. 실행과 확인

팀 공통 Python 환경과 requirements를 우선 확인한다. 원래 개발 PC는 `project3` conda 환경에 Streamlit을 설치했다. requirements에는 Streamlit이 있으나 버전은 고정되어 있지 않다.

```powershell
# 저장소 루트에서 실행. 다른 PC는 자기 환경의 python 사용.
python -m streamlit run app/app.py

# 가상환경을 사용한다면 해당 환경을 활성화한 뒤 위 명령을 실행한다.
```

모듈 수정 후 예전 문구가 남으면 Streamlit 서버를 재시작하고 다시 질문한다. 포트가 사용 중이면 사용자 프로세스를 무작정 종료하지 않는다.

확인한 범위:

- Python 파일 문법 검사.
- 브라우저에서 질문 제출 → 탐험 탭 이동.
- 초기 중심 노드만 표시 → 길쌈노래 클릭 → 민요 클릭 → 말단 노드 표시.
- 가지 접기·처음으로 초기화.
- 아리랑 한 줄 설명 → 강강술래 설명 전환 → 닫기.

확인하지 않은 범위: 실제 RAG/Pinecone, 실평가, 모든 응답 유형의 종합 테스트, 모든 브라우저의 음성 재생, 배포 환경. 문법 검사 통과를 기능 전체 검증으로 쓰지 않는다.

다음 사람이 확인할 항목:

- 질문 전 빈 상태, 새 질문 후 모든 탭의 요청 일치 여부.
- 맞춤 수준 선택과 실제 생성 결과의 일치 여부.
- 실제 citation 필드 매핑, 사용 청크 ID 검증, 원문 링크 일치.
- 미평가 상태와 실평가 결과 구분, 근거와 심사 의견 추적.
- 지도 펼치기·접기·말단 설명·초기화·좁은 화면·키보드 조작.
- 긴 문자열/HTML처럼 보이는 질문도 안전하게 표시되는지.
- 탭 전환이나 버튼 클릭으로 유료 요청이 중복 발생하지 않는지.

## 8. 권장 진행 순서

1. 코드·브랜치·최신 계약을 읽고 Mock과 실측을 명확히 구분한다.
2. UI에만 영향을 주는 오류와 표시 불일치부터 수정한다.
3. 맞춤 설명 수준 선택과 요청 묶음 구조를 준비한다.
4. RAG 담당의 실제 응답 예시·호출 함수를 받아 어댑터로 연결한다.
5. 같은 요청의 검색/사용 근거를 과정 탭에 연결한다.
6. 실평가 결과와 별도 심사 의견을 안전하게 연결한다.
7. 탐험 지도 노드 클릭과 서버의 관련 검색을 연결하고 근거 있는 한 줄 설명을 받는다.
8. 시연 질문으로 화면을 확인한 뒤 커밋·PR을 준비한다. PR 설명에는 완료 기능과 Mock/미연결 항목을 함께 쓴다.

팀이 현재 UI를 그대로 쓸지 재구현할지는 선택할 수 있다. 다만 네 탭의 목적, 같은 질문 결과 공유, 클릭한 노드에서 직접 확장, 마지막 가지의 한 줄 설명, 맞춤 답변이라는 핵심 요구는 유지한다.
