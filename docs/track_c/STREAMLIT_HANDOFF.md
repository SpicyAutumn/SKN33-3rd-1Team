## 1. 무엇이 진짜이고 무엇이 임시인가

이걸 구분하지 못하면 "다 됐다"고 잘못 보고하게 된다.

**실제로 동작하는 것**

- 질문 → OpenAI 임베딩 → Pinecone 검색 → 근거 반환
- 출처 표시, 근거 문장, 원문 링크 (모두 실제 백과사전 데이터)
- 같은 문서 청크 묶기
- 설명 수준 선택과 전달 (`audience_level`)
- 평가 탭의 검색 품질 지표
- 탐험 지도의 연결 관계 (분야·시대·유형·지역·이칭)
- 공정 견학의 6단계와 원문 역추적

**임시로 채워 둔 것 — 실제 구현이 오면 지운다**

```python
# app/rag_client.py
EvidencePassthroughGenerator   # 답변 문장을 만들지 않고 검색 원문만 전달
ScoreEvidenceChecker           # 유사도 기준선(0.40)만 보는 근거 판정
```

두 클래스 모두 `[제거 예정]` 주석이 달려 있다. 왜 필요한지는 3절에 있다.

**아직 없는 것**

- 답변 문장 생성 (생성 담당 작업 대기)
- RAGAS 점수, LLM 심사 (평가 담당 작업 대기)
- `related_topics` (계약상 기본 비활성)
- 탐험 지도 노드 클릭 시 재검색

## 3. 왜 임시 구현이 필요한가 — 지우기 전에 읽을 것

`RagService`를 그냥 쓰면 **모든 질문이 보류로 나온다.** 두 가지 이유다.

```python
# src/rag_service/service.py
def __init__(self, *, retriever, generator: GenerationComponent, ...)
                                 # ↑ 필수 인자인데 구현체가 없다

def _decide_grounding(self, question, contexts):
    ...
    if self.evidence_checker is None:
        return "insufficient"    # ↑ 없으면 무조건 보류
```

그래서 Track C가 계약 인터페이스를 따르는 최소 구현을 넣어 뒀다.
**실제 구현이 오면 `build_service()`의 인자 두 개만 바꾸면 된다.**

```python
# app/rag_client.py
return RagService(
    retriever=PineconeRetriever(),
    generator=EvidencePassthroughGenerator(),   # ← 여기
    evidence_checker=ScoreEvidenceChecker(),    # ← 여기
)
```

`EvidencePassthroughGenerator`의 유일한 규칙은 **근거 밖 문장을 지어내지 않는 것**이다. 검색된 원문만 그대로 넘긴다. 이 규칙을 깨는 방향으로 고치지 말 것.

## 4. 탭 간 상태 공유

`RagService.answer_with_trace()`의 반환 구조를 그대로 세션에 싣는다.

```python
last_result = {
    "question": str,
    "audience_level": "easy" | "general" | "advanced",
    "response": ServiceResponse,        # 계약 9장. retrieved_contexts 없음에 주의
    "retrieved_contexts": [...],        # 실행 추적. 검색 결과 전체
    "used_chunk_ids": [...],            # 근거로 쓰인 청크
    "retrieval_top_k": int,
    "related_keywords": [...],          # response["related_topics"]
}
```

**주의**: `ServiceResponse`에는 `retrieved_contexts`가 없다. 검색 결과가 필요하면 반드시 `execution["retrieved_contexts"]`에서 읽어야 한다. 이걸 `response`에서 찾다가 질문 기록이 항상 비는 버그가 있었다.

- `question_history`: 최근 10건의 질문·제목.
- `clarification_context`, `interaction_id`: 추가 질문 선택 시 담기고 다음 요청에 전달된다.
- 지도에서 펼친 상태는 iframe JavaScript 안에만 있다. 탭 전환·재실행 시 유지되지 않는다.
- `session_state`는 영구 저장이 아니다. 새 세션·재접속에는 사라진다.
- `st.cache_data`를 사용자별 질문 보관함으로 쓰지 않는다. 공유 캐시에 개인정보가 섞이면 안 된다.

## 5. 점수 기준선은 두지 않는다

팀 결정(2026-09-01)에 따라 점수 기준선을 없앴다. `TEMP_EVIDENCE_MIN_SCORE`, `meets_threshold()`, 화면의 기준선 표시가 모두 사라졌다. 근거 판정은 `ContentEvidenceChecker`가 **내용이 있는지만** 본다.

### 화면에는 유사도를 보여 준다

하이브리드 검색은 RRF로 순위를 합치면서 `retrieval_score`를 융합 점수로 덮어쓴다. 그 값은 기본 가중치에서 최댓값이 `2.5/61 ≈ 0.041`이라 화면에 `0.0397` 같은 숫자가 뜬다. 팀의 다른 검색 결과는 모두 `0.4~0.5`대 유사도라 **같은 대상을 두고 자릿수가 다른 숫자**를 보게 된다.

그래서 `HybridWithSimilarity`가 순위만 하이브리드에서 가져오고, 점수는 융합 전 밀집 검색이 매긴 유사도를 되살려 넣는다.

```
검색 3건 · 경복궁에 대해 알려줘
  1위  유사도 0.388  경복궁
  2위  유사도 0.381  경복궁
  3위  유사도 0.411  금관조복
```

**순위와 유사도 순서는 일치하지 않는다.** 3위가 유사도는 가장 높다. 낱말 일치를 함께 봤기 때문이고, 그게 하이브리드가 하는 일이다.

그대로 두면 1위 숫자가 2·3위보다 낮아 보여 **순위가 잘못된 것처럼 읽힌다**(2026-09-01 Track A 검토 의견). 그래서 이름을 `의미 유사도`로 적고, 숫자 목록 바로 위에 `retrieval.score_caption()`을 붙여 참고값임을 밝힌다. 각주로 아래쪽에 달면 못 본다.

`1·2위 격차` 같은 표기는 유사도가 순위 순으로 내려간다는 전제가 필요하므로 쓰면 안 된다 — 음수가 나온다. 의미 검색 단독일 때는 순위와 숫자 순서가 같으므로 설명 문구도 그에 맞게 바뀐다.

낱말 검색으로만 올라온 조각은 유사도를 잰 적이 없다. 계약대로 `score_type="unknown"`으로 두고 화면에는 `—`로 적는다. 0으로 적으면 가장 안 비슷한 것처럼 보인다.

### 문서당 제한 없음

`pick_evidence()`는 내용이 있는 조각을 검색 순서대로 최대 3개 고른다. **같은 문서인지 보지 않는다.** 문서당 제한은 검색 단계에서 다룰 일이지 화면 직전에 자를 일이 아니다. 출처 카드는 `group_by_document()`가 문서 단위로 묶어 보여 준다.

## 5-2. 탐험 지도 — 무엇을 재료로 쓰는가

이전 판은 **그 질문에서 검색된 청크 3개**만 재료로 썼다. 이어 붙일 항목이 많아야 둘이라 지도라고 부르기 어려웠다. 75,835건 가운데 3건만 보고 그린 셈이다.

재료를 둘로 나눴다. 데이터 계층은 `app/heritage_graph.py`, 화면은 `app/tabs/explore.py`다.

| 재료 | 규모 | 비용 | 무엇에 쓰나 |
| :--- | ---: | :--- | :--- |
| `data/manifest.csv` | 75,835건 | 없음 (저장소에 있음) | 축 값, 후보 풀, 제목·분야·유형·시대 |
| Pinecone 메타 필터 검색 | 전체 색인 | 가지당 쿼리 1회 | 후보가 수백 건일 때 무엇을 보여줄지 |

### 이웃은 질문이 아니라 그 문서의 벡터로 찾는다

제목만 임베딩하면 `경복궁`이 `계궁`·`양궁`처럼 **글자만 닮은** 낱말과 붙는다. 이미 색인된 그 문서의 벡터를 그대로 써서 문서 대 문서로 비교한다. `Neighbors.anchor()`가 정의 문단의 청크 id를 찾아 두고, 같은 조회로 설명 문장까지 챙긴다.

**BM25는 지도에 관여하지 않는다.** 낱말 겹침이 필요한 자리는 `딸린 유산`뿐인데 거기는 제목 앞머리 일치로 더 정확하게 처리한다.

### 가지 다섯

```
딸린 유산      제목이 뿌리 이름으로 시작        (만든 목록)
시대 : 조선    era 대분류 일치                 (Pinecone 필터)
종류 : 유적    primary_type 대분류 일치        (Pinecone 필터)
지역 : 서울    제목 앞머리 또는 주소            (만든 목록)
다른 갈래      뿌리와 다른 종류                 (Pinecone 필터)
```

가지 안의 순서는 모두 뿌리 문서와의 유사도다. 한 항목은 **먼저 걸린 가지에만** 넣는다. 여러 가지에 매달리면 로드맵이 아니라 그물이 된다.

`딸린 유산`은 보여 주지 못한 것까지 전부 예약한다. 그러지 않으면 `시대 : 조선`이 온통 `경복궁 ○○`으로 채워져 다른 유산으로 갈 길이 막힌다.

### 두 가지 기준 — 지우면 이상한 것이 올라온다

**추천 대상은 문화유산만.** `HERITAGE_TYPES`에 없는 인물·개념·제도·단체·지명·사건은 뺀다. 이 기준이 없으면 `궁궐`(유형 `개념`)을 뿌리로 삼았을 때 `영`·`장`·`서`·`주` 같은 한문학 용어가 추천으로 나온다. 유사도가 0.66이라 **점수로는 걸러지지 않는다.** 종류로 걸러야 한다.

**`미상` 같은 값으로는 잇지 않는다.** 6,586건이 함께 달고 있어 같은 값이라는 사실이 아무것도 설명하지 못한다.

### 뿌리를 검색 1위로 정하면 안 된다

`직지`를 물으면 1위가 `직`(유교 개념)이고 정답은 2위다. `거북선에 대해 알려줘`는 1위가 `거북점`이다. **뿌리가 틀리면 그 아래 가지가 전부 엉뚱해진다.**

`Catalog.resolve()`가 문화유산인지 → 조각이 몇 개 나왔는지 → 제목이 질문에 들어 있는지를 차례로 본다.

### 화면은 iframe이 아니라 Streamlit 버튼이다

`exploration_map.html`을 지웠다. 노드를 눌러 다시 탐색하려면 Streamlit 재실행이 필요한데 iframe 안에서는 그 신호를 보낼 수 없다. 그래서 지금은 그래프 그림이 아니라 **가지별 버튼 목록**이다. 선으로 이은 지도로 만들려면 SVG를 버튼 위에 겹쳐야 한다.

`explore_root`·`explore_trail`·`explore_search`가 세션 상태에 있다. 새 질문을 하면 출발점이 검색 결과로 되돌아간다.

## 6. 역할 경계

- **UI / Track C**: 화면, 상태 공유, 설명 수준 선택과 전달, 응답 연결, 통합 확인.
- **생성 · Prompt · Fine-tuning 담당**: 설명 수준을 실제 답변에 적용, 답변 문장 생성.
- **RAG Chain · 통합 평가 담당**: 근거 충분성 판정, 재검색, `used_chunk_ids` 검증, Citation 조립.
- **데이터 수집 · 전처리 · 검색 담당**: 수집·정제·청킹·임베딩·적재, `RetrievedContext` 반환까지.

근거 표시를 위해 같은 청크를 Pinecone에서 다시 조회하지 않는다. Citation의 `content`는 같은 요청의 검색 결과에서 온다.

### Pinecone 주의

v1 전체 179,028개 청크가 `aks-rag-v1`, 기본 namespace에 적재돼 있다. 모델은 `text-embedding-3-small`, 1,536차원, cosine.

**UI 작업을 이유로 전체 재적재, namespace 삭제, 임베딩 재생성, 플랜 변경을 수행하지 않는다.** 키 값은 문서·코드·PR에 넣지 않는다.

## 7. 알려진 한계 — PR에서 숨기지 말 것

1. **설명 수준을 바꿔도 답변 문장은 그대로다.** 화면과 데이터 흐름만 준비돼 있고, 말투를 실제로 바꾸는 것은 생성 담당 몫이다.
2. **~~검색이 대표 질문에서 틀린다.~~ 하이브리드 검색으로 해소됐다.** `경복궁에 대해 알려줘`가 의미 검색 단독에서는 1위 `금관조복`(0.411) · 5위 `경복궁`(0.387)이었으나, BM25를 합치니 `경복궁`이 1위로 올라왔다. 다만 **BM25 인덱스가 있는 환경에서만** 그렇다. 없으면 예전 순위 그대로다.
3. **같은 문서가 top_k를 잠식한다.** 석굴암·훈민정음 모두 5건 중 3건이 동일 문서였다. 화면 묶기는 반영했으나 검색 단계 제한은 RAG Chain 후속 작업이다.
4. **RAGAS 네 지표는 미연결이다.** 점수를 지우고 설명만 남겨 뒀다. 값을 지어내 채우지 말 것.
5. **검색 1위가 늘 정답은 아니다.** `성덕대왕신종`을 물으면 `선덕여왕`이 1위로 온다. BM25는 1·2위로 정확히 찾는데 RRF 융합에서 Dense 가중치 1.5에 밀린다. 가중치를 1.0으로 낮추면 실패가 `종묘 제례악`으로 자리만 옮긴다(둘 다 Hit@1 16/18). 잃어버리는 신호는 **제목 완전 일치**다. BM25의 `exact_terms`는 그 사실을 아는데 RRF가 순위 하나로 뭉갠다. Track A에 공유했다.
6. **동명 문서에 밀리는 경우가 있다.** `수원 화성`은 궁중음악 `화성`에, `고려청자`는 같은 제목의 책에 밀린다. 지도 뿌리 선택 규칙이 문헌도 문화유산으로 치기 때문이다. 질문의 수식어(`수원`)를 제목과 대조하는 규칙을 더하면 잡힌다.
7. **지역 판별에 좌표가 없다.** 제목 앞머리와 정의 문단의 주소만 본다. 주소 표기(`서울특별시 종로구`)와 제목 표기(`서울 원각사지…`)의 단위가 달라 제목 쪽으로 맞춰서 잇는다. 좌표 기반 실제 지도는 위경도가 없어 3차 범위 밖이다.
8. **`Citation`에 유사도가 없다.** 계약에 없어서 출처 카드에 표시하지 않는다. 점수는 평가 결과·공정 견학 탭에서 본다. 나중에 붙인다면 순위가 아니라 `chunk_id`로 `RetrievedContext`를 찾아 연결할 것.
9. **TTS는 브라우저 음성 합성에 의존한다.** OS 한국어 음성과 브라우저 정책에 영향을 받는다. 정지·속도·음성 선택 기능은 없다.
10. **입력 전체를 하나의 질문으로 검색한다.** 여러 독립적인 질문을 한 번에 넣으면 일부 근거가 검색되지 않는다. 팀 합의(2026-09-01)에 따라 나눠서 답하지 않고 `needs_clarification`으로 하나만 물어봐 달라고 되돌려준다. 판정은 확실한 신호만 본다 — 물음표 둘 이상, 또는 쉼표로 세 가지 이상 나열. `창덕궁과 덕수궁은 같은 궁궐이야?`처럼 대상이 둘이어도 묻는 것이 하나면 막지 않는다. **멀쩡한 질문을 막는 쪽이 답을 못 주는 것보다 나쁘다.**
11. **범위 밖 질문은 낱말 목록으로 거른다.** `TopicScopeChecker`가 주가·시세·날씨 같은 낱말을 보고 검색 전에 막는다. 목록에 없는 표현은 놓친다. 모델에게 판정을 맡기는 편이 일반적이지만 생성 호출이 한 번 더 늘어 20초 넘게 더 걸린다. 발표에서는 0초에 걸리고 이유를 댈 수 있는 지금 방식이 낫다고 봤다.

## 8. 실행과 확인

**키가 없어도 화면은 뜬다.** `.env`가 없으면 Mock 모드로, 있으면 실제 검색으로 자동 전환된다.

```bash
git fetch origin
git switch feature/track-c-score-labels

python -m venv .venv
.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt

python run.py
```

macOS/Linux는 `source .venv/bin/activate`를 쓴다.

실제 검색까지 보려면 저장소 루트에 `.env`를 만든다.

```ini
OPENAI_API_KEY=본인_키
PINECONE_API_KEY=팀_공용_키
PINECONE_INDEX_NAME=aks-rag-v1
```

> `PINECONE_API_KEY`는 **v1 인덱스가 있는 팀 계정 키**여야 한다. 개인 키를 넣으면 빈 인덱스를 보게 되어 모든 질문이 보류로 나온다. 에러가 나지 않아 원인을 찾기 어렵다.

화면 위쪽 배지로 모드를 확인한다. `🔧 Mock 응답 모드` / `✅ 실제 검색 연결됨`.

### 생성 모델은 `.env`가 정한다

모델은 바뀐다. 실제로 `Qwen3:8b`에서 `exaone3.5:7.8b-instruct-q8_0`으로 바뀌었다. 화면 문구에 이름을 박아 두면 그때마다 어긋나므로 `rag_client.generation_model()`이 `.env`의 `OLLAMA_MODEL`을 읽는다. 공정 견학 5단계는 응답이 알려 주는 `generation_metadata.model_id`를 먼저 쓰고, 없으면 설정값을 쓴다.

```ini
OLLAMA_BASE_URL=https://…-11434.proxy.runpod.net   # 11434 포트다. 8888은 Jupyter다
OLLAMA_MODEL=exaone3.5:7.8b-instruct-q8_0
OLLAMA_KEEP_ALIVE=1h
```

### BM25 인덱스는 각자 만들어야 한다 — 안 만들면 검색이 틀린다

Pinecone은 팀 공용 서버지만 **BM25는 로컬 SQLite 파일**이라 공유되지 않는다(`.gitignore: data/processed/*`). 만들지 않아도 화면은 뜨지만 **의미 검색 단독으로 내려가고 검색이 틀린다.**

```
인덱스 없음(의미 검색 단독)   직지 -> 직          거북선에 대해 알려줘 -> 거북점
전체 인덱스(하이브리드)       직지 -> 불조직지심체요절   거북선에 대해 알려줘 -> 거북선
```

`직지`는 `직`과 글자가 거의 같아 의미 검색만으로는 못 가린다(0.493 대 0.489). 낱말 검색이 있어야 갈린다. **BM25를 넣은 이유가 이것이므로 인덱스 없이 쓰면 의미가 없다.**

어느 쪽으로 검색했는지와 인덱스 크기는 공정 견학 탭 2단계에 표시된다.

만들려면 청킹 완료 JSONL이 필요하다. 저장소에는 없고 Drive에서 받아야 한다. **`aks_full_content_json.zip`이 아니라 `aks_full_chunks.jsonl`이다.** 앞의 것은 청킹 전 원본이라 그대로는 못 쓴다.

```
aks_full_chunks.jsonl   179,028줄 · 371MB   ← 이것
인덱스 생성 47초 · 결과 660MB
```

```bash
.venv/Scripts/python.exe scripts/build_aks_bm25.py --chunks data/processed/aks_full_chunks.jsonl
```

기본 출력 위치는 `data/processed/aks_bm25_v1.sqlite3`다. 다른 곳에 두려면 `.env`에 경로를 적는다.

```ini
AKS_BM25_INDEX_PATH=D:/어딘가/aks_bm25_v1.sqlite3
```

작은 인덱스로 전체 경로를 확인해 본 결과다. 청크 3건짜리 인공 인덱스라 실제 말뭉치의 성능을 뜻하지는 않지만, 배선이 동작하고 **순위 실패가 실제로 교정될 수 있다**는 것은 보여 준다.

```
질문: 경복궁에 대해 알려줘
  의미 검색 단독 ->  금관조복, 경복궁, 창덕궁
  하이브리드     ->  경복궁, 금관조복, 창덕궁
```

**확인용 질문**

| 질문 | 무엇을 보는지 |
| :--- | :--- |
| `경주 불국사에 대해 알려줘` | 답변·근거·공정 견학·탐험 지도가 모두 채워진다 |
| `석굴암 본존불의 특징은?` | 같은 문서 여러 청크가 출처 1건으로 묶인다 |
| `무령왕릉` | 탐험 지도 다섯 가지가 모두 뜬다. 노드를 눌러 재탐색 |
| `직지` | **BM25 인덱스 확인용.** 없으면 `직`(유교 개념)이 나온다 |
| `현대자동차 주가 알려` | 0초에 `범위 밖 질문`. 검색도 생성도 하지 않는다 |
| `경복궁이 뭐야? 창덕궁은 언제 지어졌어?` | 하나만 골라 달라는 화면. 고르면 바로 실행된다 |

## 9. 주의할 함정

- **`st.html`에 넣는 CSS에 날 HTML 태그를 쓰면 안 된다.** `<svg>`를 그대로 넣었더니 정화 과정에서 스타일시트 전체가 제거돼 폰트·탭·카드가 모두 무너졌다. SVG는 퍼센트 인코딩(`%3Csvg...`)해서 넣는다.
- **`st.iframe`은 `height=0`을 거부한다.** 소리만 내는 용도라도 `height=1`을 쓴다.
- **배경색·글자색을 직접 지정하지 않는다.** Streamlit 테마 값을 그대로 쓰고 강조색과 반투명 층만 얹는다. 직접 지정하면 밝은 화면과 어두운 화면 중 한쪽에서 글씨가 묻힌다.
- **`.streamlit/config.toml`은 실행 위치가 저장소 루트일 때만 읽힌다.** `python run.py`로 실행하면 정상 적용된다.

**먼저 할 것 — 환경**

1. Drive에서 `aks_full_chunks.jsonl`을 받아 BM25 인덱스 생성 (47초). 안 하면 검색이 틀린다
2. `.env`에 `OLLAMA_BASE_URL` (RunPod 주소는 tender0602님)

**바로 손댈 수 있는 것**

3. 동명 문서 문제 — `Catalog.resolve()`에 질문의 수식어(`수원 화성`의 `수원`)를 제목과 대조하는 규칙 추가. 7절 6번
4. 발표 시연 시나리오 — 8절 질문으로 전 기능을 훑는 흐름 정리. 답변 생성이 22~29초 걸리니 대기 시간을 감안할 것
5. `top_k` 슬라이더 — 평가 화면에 기본 3 / 비교 5. 공식 평가 때는 고정 (팀 합의됨)
6. 탐험 지도를 선으로 이은 그래프로 — SVG를 버튼 위에 겹쳐야 한다. 5-2절 마지막

**다른 트랙에 달린 것**

7. 제목 완전 일치 우선 — `성덕대왕신종` 문제. Track A에 공유했다. 7절 5번
8. 평가 탭 RAGAS 지표에 실측값 연결 — LLM 심사가 붙어야 한다
9. 임시 구현 제거 — 실제 `EvidenceChecker`·`ScopeChecker`가 오면 `app/rag_client.py`에서 걷어낸다

**하지 말 것**

- 근거 없이 답변 문장을 만들어 채우는 것
- 평가 점수를 임의 값으로 채우는 것
- 계약에 없는 필드를 화면 마음대로 추가하는 것
- 부분 BM25 인덱스로 검색 성능을 판단하는 것 — 인덱스 크기를 먼저 볼 것
