# 후보 주제 데이터 확보 가능성 검증서

> 문서 구분: 착수 단계 보조 산출물  
> 작성일: 2026-08-25  
> 상태: 사전 조사 완료 / 실제 표본 검증 전  
> 주의: 아래 평가는 API와 공식 사이트의 존재를 확인한 단계이며 데이터 품질 통과를 의미하지 않는다.

> [!NOTE]
> 2026-08-25 후보와 표본 계획은 1차 주제 선정 당시 기록으로 보존한다.  
> 2026-08-26 오전 원안과 이를 발전시킨 세 후보의 검증 계획은 **같은 팀원 개인이 생각하고 구상한 사전 기획안**을 바탕으로 작성했다. 두 단계는 개인 기획의 연속적인 구체화 과정이며, 팀의 합의·결정이나 데이터 확보 완료를 의미하지 않는다.

## 1. 목적

프로젝트 주제를 확정하기 전에 후보별 데이터를 실제로 확보할 수 있는지, 확보한 데이터가 RAG 검색과 답변 평가에 적합한지 확인한다. 최종 주제는 아이디어의 흥미뿐 아니라 다음 조건을 통과한 후보 중에서 선정한다.

- 신뢰 가능한 출처
- 허용된 이용 범위
- 충분한 설명문과 메타데이터
- 재현 가능한 수집·전처리 방법
- 정답과 출처를 만들 수 있는 평가 가능성
- 최신성 관리 가능성

| :--- | :--- |

점심 회의에서 상위 후보와 담당자를 정한 뒤 위 표본 수량을 실제 검증 과제로 전환한다. 회의 전에는 `표본 확보`, `RAG 검증`, `통과`로 상태를 올리지 않는다.

## 5. 공통 데이터 검증 게이트

### Gate 1 — 출처와 접근

- [ ] 제공기관과 원본 URL을 기록했다.
- [ ] API 신청, 인증 방식과 호출 제한을 확인했다.
- [ ] 동일한 절차로 다시 수집할 수 있다.
- [ ] API 장애 시 사용할 수 있는 공식 다운로드 또는 대체 자료를 확인했다.

**통과 기준:** 핵심 답변을 공식 또는 신뢰 가능한 출처로 추적할 수 있고 재수집 방법을 설명할 수 있다.

### Gate 2 — 이용 조건과 공개 가능성

- [ ] 데이터 이용약관과 라이선스를 확인했다.
- [ ] 출처표시 문구를 확인했다.
- [ ] 이미지와 본문의 이용 조건을 각각 확인했다.
- [ ] 개인정보, 저작권 제한 자료와 재배포 금지 자료를 구분했다.
- [ ] GitHub에 원본을 올릴 수 있는지 확인했다.

**통과 기준:** 저장소, 시연 화면, 발표자료에서 허용되는 이용 범위가 명확하다.

### Gate 3 — 표본 수집과 구조

- [ ] 실제 데이터 30~100건을 수집했다.
- [ ] 원본 응답을 `data/samples/<topic>/raw/`에 보관했다.
- [ ] 표본의 필드명과 자료형을 데이터 사전에 기록했다.
- [ ] 설명문이 비어 있거나 지나치게 짧은 비율을 확인했다.
- [ ] 날짜, URL, ID, 카테고리 등 필수 메타데이터를 확인했다.

**통과 기준:** RAG 본문과 출처 표시에 필요한 데이터가 실제 응답에 존재한다.

### Gate 4 — 품질과 전처리

- [ ] 결측, 중복, 깨진 인코딩과 HTML 태그를 확인했다.
- [ ] 제외 기준과 제외 건수를 기록했다.
- [ ] 전처리 전후 표본을 원문과 대조했다.
- [ ] 문서 ID와 갱신 기준을 정했다.

**통과 기준:** 전처리 후에도 원문의 의미와 출처가 유지되고 예외 처리 기준을 재현할 수 있다.

### Gate 5 — RAG 검색 적합성

- [ ] 대표 질문 10건 이상을 작성했다.
- [ ] 문서 단위와 청크 단위 검색을 비교했다.
- [ ] 청크 크기와 `top_k`의 초기값을 정했다.
- [ ] 메타데이터 필터가 필요한 질문을 확인했다.
- [ ] 관련 근거가 상위 검색 결과에 포함되는지 기록했다.

**통과 기준:** 대표 질문에서 필요한 근거 문서가 상위 검색 결과에 반복적으로 나타난다.

### Gate 6 — 답변과 거절 평가

- [ ] 답할 수 있는 질문, 비교 질문, 답변 불가 질문을 구분했다.
- [ ] 예상 답변과 기대 출처를 기록했다.
- [ ] 문서 밖 질문에 추측하지 않는지 확인했다.
- [ ] 위험한 최종 판단을 요청하는 질문을 포함했다.

**통과 기준:** 정확성, 출처 일치, 근거 충실성, 답변 거부를 동일한 기준으로 평가할 수 있다.

### Gate 7 — 갱신과 운영

- [ ] 데이터 기준일을 답변에 표시할 수 있다.
- [ ] 재수집 주기와 담당자를 정했다.
- [ ] 변경 또는 삭제된 문서의 벡터 갱신 방법을 정했다.
- [ ] 오래된 데이터와 최신 API 정보가 충돌할 때의 처리 방법을 정했다.

**통과 기준:** 오래된 데이터가 최신 정보처럼 노출되지 않도록 운영 규칙이 존재한다.

## 6. 표본 폴더 권장 구조

```text
data/
└── samples/
    ├── heritage/
    │   ├── raw/
    │   ├── processed/
    │   └── sample_inventory.csv
    ├── qualification/
    │   ├── raw/
    │   ├── processed/
    │   └── sample_inventory.csv
    └── welfare/
        ├── raw/
        ├── processed/
        └── sample_inventory.csv
```

공개가 허용되지 않거나 용량이 큰 원본은 Git에 올리지 않는다. 이 경우 `sample_inventory.csv`에는 실제 원문 대신 다음 정보만 기록한다.

| 필드 | 설명 |
| :--- | :--- |
| `sample_id` | 표본 식별자 |
| `topic` | 후보 주제 |
| `source_name` | 제공기관·문서명 |
| `source_url` | 공식 원본 URL |
| `collected_at` | 수집일 |
| `format` | JSON, XML, HTML, PDF 등 |
| `license` | 이용 조건 |
| `public_allowed` | GitHub 공개 가능 여부 |
| `included` | 검증 포함 여부 |

## 8. 최종 선정 기준

최종 주제는 다음 조건을 모두 충족한 후보 중에서 선택한다.

1. 신뢰 가능한 원문을 프로젝트 기간 안에 확보할 수 있다.
2. 이용 조건과 공개 범위가 명확하다.
3. 질문의 답을 뒷받침하는 설명문과 출처가 존재한다.
4. 청크·임베딩·검색 실험을 수행할 수 있다.
5. 정답과 답변 불가 사례를 포함한 평가 세트를 만들 수 있다.
6. 사용자에게 제공해서는 안 되는 최종 판단의 범위를 정의할 수 있다.
7. 팀이 데이터 갱신과 재수집 절차를 관리할 수 있다.

검증 결과는 [주제 선정 회의 기록](../01_initial_review/topic_selection_summary.md)에 요약하고, 최종 결정은 [`decision_log.md`](../../decision_log.md)의 `DEC-001`에 기록한다. 채택한 데이터의 본 수집과 전처리 결과는 [`02_data_preprocessing_report.md`](../../02_data_preprocessing_report.md)로 이어진다.
