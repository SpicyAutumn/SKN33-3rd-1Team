# Track B 생성·Prompt·Fine-tuning 담당 역할 및 업무 범위

> 작성일: 2026-08-28  
> 상태: PR #3 팀원 리뷰 대응안 반영 — 재검토 예정  
> 승인일: 2026-08-28  
> 전제: 최소 표본을 받기 전에 착수할 수 있는 업무를 우선 정의한다.

## 1. 문서 목적

이 문서는 Track B의 생성·Prompt·Fine-tuning 담당이 수행할 생성·개인화 업무의 범위를 정한다. 팀원 사이의 중복 작업을 줄이고, 데이터 표본이 준비되기 전에도 설계 작업을 시작할 수 있도록 책임, 비책임, 협업 지점을 구분한다.

이 문서는 Fine-tuning 모델의 최종 채택을 미리 결정하지 않는다. Prompt Baseline과 Fine-tuning 모델을 같은 조건에서 비교한 결과에 따라 채택 또는 미채택 의견을 제시하는 것까지를 생성·Prompt·Fine-tuning 담당의 책임으로 본다.

## 2. 생성·Prompt·Fine-tuning 담당의 업무 목표

> 검색된 동일한 근거를 사용해 `쉽게`, `일반`, `깊이 있게` 수준의 답변을 일관된 형식으로 생성하고, Prompt Baseline과 Fine-tuning 모델을 동일 조건에서 비교하여 Fine-tuning의 필요성과 효과를 설명한다.

Fine-tuning은 역사·문화 지식을 모델에 암기시키는 용도로 사용하지 않는다. 문서 지식과 출처는 RAG가 담당하고, 생성·Prompt·Fine-tuning 담당은 다음 생성 행동의 개선 가능성을 검증한다.

- 설명 수준에 맞는 표현
- 합의된 응답 형식 준수
- 검색 근거 밖 내용의 생성 억제
- 근거가 부족할 때 답변을 보류하는 표현
- 딱딱한 원문을 자연스럽게 설명하되 사실과 출처를 유지하는 행동

## 3. 생성·Prompt·Fine-tuning 담당의 직접 책임

| 영역 | 책임 | 주요 산출물 |
| :--- | :--- | :--- |
| 목표 행동 정의 | Fine-tuning으로 개선하려는 행동과 성공 기준 정의 | 역할 정의서, 목표 행동 목록 |
| Prompt Baseline | Fine-tuning 전 비교 기준이 되는 Prompt 설계·버전 관리 | Prompt Baseline 문서와 템플릿 |
| 생성 응답 규격 초안 | 생성 모듈이 반환할 구조화된 응답 형식 제안 | 응답 스키마 초안 |
| 생성 컴포넌트 | RAG Chain·통합 평가 담당이 전달한 고정 검색 문맥을 입력받아 Prompt → Model → Parser를 수행하는 독립 모듈 | 생성 코드와 단위 테스트 |
| 학습 데이터 설계 | 학습 예제 형식, 작성 기준, 검수 상태, 데이터 분리 기준 설계 | 학습 데이터 명세와 검증 규칙 |
| Fine-tuning | 승인된 데이터와 모델을 사용한 학습 및 실험 기록 | 학습 설정, 모델 식별 정보, 실행 결과 |
| 전후 비교 | 동일 평가 세트와 고정 조건을 사용한 Baseline 대비 비교 | 비교표, 실패 사례, 비용·성능 분석 |
| 채택 의견 | 결과에 근거한 적용·미적용 또는 추가 실험 의견 작성 | Fine-tuning 채택 판단안 |

## 4. 초안 역할의 반영 범위

초안의 `Prompt`, `응답 스키마`, `RAG Chain` 중 다음 내용을 생성·Prompt·Fine-tuning 담당의 업무에 반영한다.

| 초안 업무 | 반영 방법 | 최종 책임 |
| :--- | :--- | :--- |
| Prompt | Prompt Baseline과 수준별 개인화 Prompt로 유지 | 생성·Prompt·Fine-tuning 담당 |
| 응답 스키마 | 생성·Prompt·Fine-tuning 담당이 초안을 만들고 전처리·검색 데이터, RAG Chain·통합 평가, UI·배포 담당과 인터페이스를 합의 | 생성·Prompt·Fine-tuning 담당 초안, 공동 승인 |
| RAG Chain | RAG Chain·통합 평가 담당이 서비스 RAG Chain 전체를 담당한다. 생성·Prompt·Fine-tuning 담당은 Retriever를 포함한 별도 Chain을 만들지 않고, 고정된 검색 문맥을 받는 생성 실험 실행기만 구성한다. | RAG Chain·통합 평가 담당: 서비스 RAG Chain, 생성·Prompt·Fine-tuning 담당: 생성 구간·오프라인 실험 |

생성·Prompt·Fine-tuning 담당이 구현하는 생성 컴포넌트는 다음과 같은 경계를 가진다.

```text
사용자 질문
    ↓
RAG Chain·통합 평가 담당: 안전·서비스 범위 사전 판정
    ↓
전처리·검색 데이터 담당의 Retriever 호출
    ↓
RAG Chain·통합 평가 담당: 근거 충분성 판정·필요 시 재검색
    ↓
생성·Prompt·Fine-tuning 담당: Prompt → Model 후보 → Output Parser
    ↓
RAG Chain·통합 평가 담당: 근거·안전 검증, 최종 응답 유형·출처 결정
    ↓
UI·배포 담당: Streamlit 화면 표시
```

위 구조는 팀 회의에서 정한 역할을 변경하기 위한 것이 아니다. `RAG Chain·LLM·안전장치·통합 평가`와 `Fine-tuning 데이터·모델 학습·비교`의 주 담당을 구분한 기존 합의를 그대로 유지한다.

시간 제약이 있으면 생성·Prompt·Fine-tuning 담당은 서비스 RAG Chain 구현을 기다리지 않고, 합의된 `GenerationRequest`와 고정 검색 문맥을 사용해 생성 실험을 병렬로 진행할 수 있다.

```text
RAG Chain·통합 평가 담당이 제공한 동일 검색 문맥·질문·생성 설정
                    │
            ┌───────┴───────┐
            ▼               ▼
     Prompt Baseline    Fine-tuning 후보
            └───────┬───────┘
                    ▼
             동일 기준으로 비교
                    ▼
       채택 후보를 서비스 RAG Chain 흐름에 연결
```

이 오프라인 비교는 서비스 RAG Chain 구현이 아니다. 공정한 비교를 위해 입력 검색 문맥, 질문 세트, 생성 설정, 응답 형식과 평가 기준을 같게 맞춘다. 모델 후보의 인터페이스가 다르면 `0.3.0-draft` 공통 입출력 형태로 변환하는 Adapter를 사용한 뒤 비교한다.

## 5. 생성·Prompt·Fine-tuning 담당의 비책임 범위

다음 업무는 생성·Prompt·Fine-tuning 담당의 단독 책임으로 두지 않는다.

| 업무 | 주 담당 | 생성·Prompt·Fine-tuning 담당의 참여 범위 |
| :--- | :---: | :--- |
| 원문 수집·이용조건·Document Card | 데이터 수집·이용조건 담당 | 학습 데이터에 필요한 필드 의견 제공 |
| 청킹·임베딩·Vector DB | 전처리·검색 데이터 담당 | 생성 입력에 필요한 검색 결과 형식 협의 |
| Hit@k·MRR 등 검색 성능 평가 | 전처리·검색 데이터 담당 | 검색 실패와 생성 실패 구분에 참여 |
| 서비스 RAG Chain·검색 호출·재검색·근거 충분성 판정 | RAG Chain·통합 평가 담당 | 생성 컴포넌트 연결과 보류 표현 협의 |
| 사전 안전·범위 판정·최종 `response_type`·출처 조립 | RAG Chain·통합 평가 담당 | Prompt와 학습 예시가 최종 규격을 따르도록 지원 |
| 프롬프트 인젝션·비밀정보 등 통합 안전장치 | RAG Chain·통합 평가 담당 | 학습 예시와 생성 Prompt 측면에서 지원 |
| Streamlit·UX·배포 | UI·배포 담당 | 응답 필드와 수준 선택값 협의 |
| 프로젝트 범위·비용·최종 모델 채택 결정 | 프로젝트 관리·팀 의사결정 담당과 팀 전체 | 실험 결과와 권고안 제공 |

생성·Prompt·Fine-tuning 담당이 Fine-tuning 모델을 만들었다는 이유만으로 최종 서비스에 적용하지 않는다. 최종 채택은 팀의 통합 평가와 비용·일정 검토를 거쳐 결정한다.

## 6. 팀원과 반드시 협업하거나 논의할 사항

### 6.1. 전처리·검색 데이터 담당과 협의

- Retriever가 생성·Prompt·Fine-tuning 담당에게 전달할 값과 자료형
- 각 검색 문서의 `document_id`, 제목, 본문, URL 등 메타데이터
- 검색 결과가 없거나 일부 필드가 비어 있을 때의 처리 방식
- 검색 실패와 생성 실패를 구분하는 기록 방법

**논의 시점:** 2단계 생성 입출력 계약 승인 전

### 6.2. RAG Chain·통합 평가 담당과 협의

- 생성 컴포넌트를 서비스 RAG Chain에 연결하는 방법
- Prompt Baseline과 Fine-tuning 후보를 비교할 때 같게 고정할 검색 문맥·질문·생성 설정·평가 기준
- RAG Chain·통합 평가 담당이 결정한 `grounding_decision`을 생성 컴포넌트가 처리하는 방법
- 생성 단계의 잠정 응답과 RAG Chain 검증 후 최종 `response_type`이 다를 때의 처리 방법
- 답변 보류 상태와 보류 사유의 표현
- 생성 단계의 수준별 표현 평가와 RAG Chain의 Faithfulness·인용·통합 평가 경계
- Prompt 인젝션 등 안전장치가 Prompt 및 학습 예시에 미치는 영향

**논의 시점:** 생성·Prompt·Fine-tuning 담당은 고정 Mock Context를 사용한 생성 실험을 먼저 시작할 수 있다. 다만 실제 통합 전에는 연동 필드와 근거 판정 정책을, 비교 평가 전에는 고정 조건을 RAG Chain·통합 평가 담당과 함께 확인한다.

### 6.3. UI·배포 담당과 협의

- 설명 수준 선택값과 기본값
- UI에서 반드시 필요한 응답 필드
- 출처, 관련 항목, 답변 보류 상태의 화면 표시 방법
- Mock 응답과 실제 응답이 같은 구조를 사용하도록 하는 방법

**논의 시점:** 2단계 응답 스키마 승인 전

### 6.4. 데이터 수집·이용조건 담당과 협의

- 원문과 학습 예제에서 사용할 수 있는 필드
- 문서 저장·가공·외부 모델 전송 가능 범위
- 학습 데이터에 출처 원문을 어느 범위까지 포함할 수 있는지
- 실제 자료에서 확인할 수 없는 값을 임의 생성하지 않는 기준

**논의 시점:** 4단계 학습 데이터 명세 승인 전

### 6.5. 프로젝트 관리·팀 의사결정 담당 및 팀 전체와 협의

- 팀 회의에서 정한 생성·학습과 RAG 통합의 주 담당을 유지하고, 오프라인 생성 비교와 서비스 RAG Chain을 구분하는 원칙
- `쉽게`, `일반`, `깊이 있게`의 표현 기준
- 사용할 Baseline 모델과 Fine-tuning 가능 모델
- 외부 API 사용, 학습 비용과 실행 환경
- Fine-tuning 채택 기준과 결과 발표 방식

**논의 시점:** 역할 범위 승인 전 또는 각 관련 단계 승인 전

## 7. 최소 표본 전후의 업무 경계

### 최소 표본 전 가능

- 역할과 목표 행동 정의
- 입출력 계약 및 응답 스키마 설계
- Prompt Baseline 초안 작성
- 학습 데이터 스키마와 품질 기준 설계
- 평가 기준과 비교표 설계
- Mock Context 기반 생성 코드 작성
- 데이터 검증 및 학습 실행 코드 골격 작성

### 최소 표본 후 가능

- 실제 Prompt Baseline 측정
- 실제 문서 근거를 사용한 학습 예제 작성·검수
- Train·Validation·Test 데이터 분리
- Fine-tuning 실행
- 동일 평가 세트의 전후 비교
- 최종 모델 채택 또는 미채택 판단

## 8. 단계 완료 기준

다음 항목이 승인되면 Track B 생성·Prompt·Fine-tuning 담당의 역할 범위가 확정된 것으로 본다.

- 생성·Prompt·Fine-tuning 담당이 개선하려는 목표 행동
- 생성·Prompt·Fine-tuning 담당의 직접 책임과 비책임 범위
- Prompt·응답 스키마·서비스 RAG Chain의 역할 경계
- 데이터 수집, 전처리·검색 데이터, RAG Chain·통합 평가, UI·배포, 프로젝트 관리 담당과 논의해야 할 항목과 시점
- Fine-tuning 결과가 좋지 않을 경우 미채택도 유효한 산출물이라는 원칙

승인 전에는 응답 스키마 설계나 Prompt 작성 등 다음 단계로 넘어가지 않는다.

## 9. 현재 승인 또는 팀 논의가 필요한 항목

| 번호 | 항목 | 제안 | 필요한 결정 주체 | 상태 |
| :---: | :--- | :--- | :---: | :---: |
| R-01 | 생성·Prompt·Fine-tuning 담당의 핵심 목표 | 수준별 표현·형식·근거 기반 행동 개선 및 전후 비교 | 사용자·팀 | 사용자 승인·팀 확인 예정 |
| R-02 | 전체 RAG Chain 책임 | RAG Chain·통합 평가 담당이 서비스 Chain 전체를 맡고, 생성·Prompt·Fine-tuning 담당은 고정 검색 문맥 기반 생성 구간과 오프라인 비교를 담당 | 생성·Prompt·Fine-tuning 담당, RAG Chain·통합 평가 담당, 팀 | 리뷰 대응안 확정·재검토 예정 |
| R-03 | 응답 스키마 책임 | 생성·Prompt·Fine-tuning 담당이 초안을 작성하고 전처리·검색 데이터, RAG Chain·통합 평가, UI·배포 담당이 공동 검토 | 관련 담당자 공동 | 사용자 승인·공동 검토 예정 |
