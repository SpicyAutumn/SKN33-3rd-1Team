## 3. 1차 회의 이후 변경 배경

### 3.1. 강사 피드백

`의견`

> B2B 또는 B2C와 연결할 수 있고 취업·포트폴리오에 활용할 수 있을 정도의 주제를 검토할 필요가 있다.

### 3.2. 현재 해석

단순히 서비스에 `B2B` 또는 `B2C`라는 이름을 붙이는 것이 아니라 다음을 설명할 수 있어야 한다.

1. 사용자는 누구인가?
2. 비용을 지불하거나 도입을 결정하는 고객은 누구인가?
3. 고객의 어떤 업무 또는 불편을 개선하는가?
4. 공식적이고 신뢰할 수 있는 데이터를 확보할 수 있는가?
5. LLM·RAG가 문제 해결의 핵심인가?
6. 교육 기간 안에 MVP 구현과 성능 평가가 가능한가?

### 3.3. 기존 문화유산 도슨트의 변화 가능성

#### 오전 원안 — 팀원 개인 기획안

```text
기존 방향
일반 관람객이 문화유산에 질문하는 B2C형 AI 도슨트

변경·확장 후보
1. 문화유산 굿즈 상품기획 지원
2. 박물관·학교 연계 역사교육 콘텐츠 제작과 학습진단
3. 기존 도슨트 유지 후 고객·업무·평가 구조 구체화
```

#### 현재 사전 구체화안 — 오전 개인 기획안의 후속 구체화

| 후보 | 오전 제안 | 현재 구체화안 | 점심 회의 확인사항 |
|---|---|---|---|
| 역사교육 | 초·중등 교과과정과 한국사능력검정시험을 포괄한 교육 프로그램 | 중학생 한국사 초심자를 대상으로 한 박물관·교사용 콘텐츠 제작·검수 및 학습진단 플랫폼 | 핵심 B2B 사용자를 박물관 담당자와 교사 중 누구로 할지 확인 |
| 문화유산 굿즈 | 지역업체와 재료 수급부터 디자인·제조까지 연계 | 유물·고객·상품·제작조건을 바탕으로 기획안과 디자인 방향을 비교하는 의사결정 지원 시스템 | 유물 수, 제품군 수, 실제 업체 데이터 확보 여부 확인 |
| 길 안내 | 주차·단속·리뷰·그늘·교통법규를 포괄한 길 안내 발전형 | 특정 시설 한 곳의 주차장·대중교통·관람·날씨·주변 일정을 통합하는 방문 계획 도우미 | 대상 시설·서비스 반경·실시간 API 범위 확인 |

현재 세 후보의 공통 상태는 `사전 구체화 — 팀 합의 전`이다.

### 3.4. 별도 신규 주제

#### 오전 원안 — 팀원 개인 기획안

- 목적지 주변 주차장 탐색과 재경로 안내
- 주정차 금지·단속 위험 정보
- 리뷰 분석과 대체 장소 추천
- 그늘·우천 회피 보행 경로
- 초보운전자를 위한 교통 상황 설명

#### 현재 구체화에 따른 분류

| 오전 아이디어 | 현재 분류 | 사유 |
|---|---|---|
| 목적지 주변 주차장 탐색 | 방문 계획 도우미의 핵심 기능 | 시설 방문 전 대안 비교에 직접 필요 |
| 대중교통·관람정보 통합 | 방문 계획 도우미의 핵심 기능 | 이동과 관람을 하나의 사용자 일정으로 연결 |
| 주정차 금지·단속 판단 | 제외 후보 | 현재 단속 여부를 보장하기 어려움 |
| 리뷰 작성자 신뢰도 판정 | 보류 후보 | 이용약관·개인정보·공정성 문제 |
| 그늘·우천 회피 경로 | 확장 후보 | GIS·3D 공간정보와 경로 최적화 의존도가 높음 |
| 초보운전자 상황 설명 | 별도 후보 | 방문 계획과 해결하려는 문제가 다름 |

## 4. 팀원별 의견 취합

> 팀원의 발언을 가능한 한 원문에 가깝게 먼저 기록한 뒤, 아래쪽에 회의에서 정리한 내용을 작성한다.
> 이 절의 A~D는 이번 2차 회의에서만 사용하는 익명 표기이며 1차 회의의 표기와 연결하지 않는다.

### 4.1. 팀원 A

| 항목 | 기록 |
|---|---|
| 제안 주제 | 재난 관련 공공서비스 제공 |
| 의견 원문 요약 | 재난 상황에서 안내·대피 등 공공서비스를 제공하는 방향 |
| 문제를 겪는 사용자 | 회의에서 구체화되지 않음 |
| 도입·구매 고객 | 회의에서 구체화되지 않음 |
| 해결하려는 문제 | 재난 상황의 정보 안내와 대피 지원 |
| 핵심 기능 | 안내, 대피 지원 |
| 데이터 후보 | 회의에서 제시되지 않음 |
| 우려 또는 제한 | 서비스 범위, 대상 재난, 실시간 데이터, LLM·RAG의 역할이 아직 미정 |
| 제안자가 원하는 역할 | 회의에서 제시되지 않음 |

**회의에서 확인할 질문**

- 이 문제는 실제로 누구에게 얼마나 자주 발생하는가?
- LLM 또는 RAG가 없다면 어떤 부분을 해결하기 어려운가?
- 첫 번째 버전에서 반드시 필요한 기능은 무엇인가?

**회의 후 정리:** 재난 종류·핵심 사용자·공식 데이터·실시간성·오안내 위험을 먼저 구체화할 필요가 있다.  

**상태:** `추가 조사`

### 4.2. 팀원 B

| 항목 | 기록 |
|---|---|
| 제안 주제 | 개인 맞춤형 AI 문화유산 여행 도슨트 |
| 의견 원문 요약 | 관심사·연령·여행시간·위치에 맞춰 문화유산을 추천하고 이야기형 설명을 제공하는 AI |
| 문제를 겪는 사용자 | 문화유산 정보를 직접 검색하기 어렵고 긴 설명을 부담스러워하는 여행자 |
| 도입·구매 고객 | 회의에서 구체화되지 않음 |
| 해결하려는 문제 | 기존 문화유산 정보가 길고 딱딱하며 사용자가 일일이 검색해야 하는 불편 |
| 핵심 기능 | 맞춤 여행코스 생성, 지도, 장소 선택, AI 도슨트, 자유 질문, 퀴즈·스탬프 |
| 데이터 후보 | 공식 문화유산 데이터, 사용자 관심사·연령·여행시간·위치 |
| 우려 또는 제한 | 일반 Gemini·ChatGPT로도 가능한지 차별성 검토 필요; Fine-tuning 필요성은 실험 전 미확정 |
| 제안자가 원하는 역할 | 회의에서 제시되지 않음 |

**회의 후 정리:** RAG는 공식 사실·출처 검색에 사용하고, 딱딱한 설명을 여행자용 이야기로 바꾸는 방법으로 Fine-tuning을 제안했다. 기존 방문 도우미와 결합하여 구체화하기로 했으나 결합 범위는 아직 정하지 않았다.  

**상태:** `통합` — 후속 구체화 예정

| 항목 | 기록 |
|---|---|

| 의견 원문 요약 | 세 주제 중 굿즈는 다소 어려워 보이며, 굿즈 기획·디자인보다 기존 굿즈와 문화유산 또는 사용자를 연결하는 형태 검토 제안 |
| 문제를 겪는 사용자 | 회의에서 별도로 구체화되지 않음 |
| 도입·구매 고객 | 회의에서 별도로 구체화되지 않음 |
| 해결하려는 문제 | 굿즈 기획·디자인·제작조건 데이터 확보와 구현 난도 완화 |

| 우려 또는 제한 | 기존 굿즈 데이터의 확보·이용조건과 단순 상품 추천과의 차별성 확인 필요 |
| 제안자가 원하는 역할 | 회의에서 제시되지 않음 |

**회의 후 정리:** 굿즈 후보는 현재 기획·디자인 지원안을 그대로 확정하지 않고, 기존 굿즈 연결형 대안과 함께 후속 정리한다.  

**상태:** `구체화` — 후속 정리 예정

### 4.4. 팀원 D

| 항목 | 기록 |
|---|---|
| 제안 주제 | RAG·Agent 기반 LLM 서비스 보안 위험 분류 및 공식 가이드 제공 시스템 |
| 의견 원문 요약 | 보안 전문성이 부족한 AI 개발자가 설계 단계에서 중요한 보안 항목을 놓치지 않도록 위험 유형·점검 근거·대응 방향·출처를 제공 |
| 문제를 겪는 사용자 | RAG·Agent 서비스를 설계하지만 보안 전문성이 부족한 AI 개발자; 보안 점검을 지원하는 담당자 |
| 도입·구매 고객 | 사내 AI·RAG 서비스 개발 조직 가능성이 언급됐으나 구매·도입 주체는 미확정 |
| 해결하려는 문제 | 개발 시점에서 우선 점검할 보안 위험과 확인 질문을 체계적으로 파악하기 어려움 |
| 핵심 기능 | 서비스 상황 추가 질문, 위험 유형 분류, 우선순위 표시, 공식 근거와 대응 방향 제시 |
| 데이터 후보 | OWASP·NIST 등 신뢰할 수 있는 보안 문서 |
| 우려 또는 제한 | 보안 전문가용 자동화 도구가 아니라 개발자용 설계 점검 지원으로 범위를 정해야 하며 구체 MVP는 미정 |
| 제안자가 원하는 역할 | IT 분야 포트폴리오에 도움이 되는 방향 검토 |

**회의 후 정리:** `공통 Vector DB 사용 여부`, `문서별 접근권한`, `외부 업로드 문서`, `외부 LLM API 전달 여부` 등을 추가 질문한 뒤 Retrieval Access Control, Indirect Prompt Injection, Sensitive Information Disclosure 등의 위험 우선순위를 제시하는 흐름을 예시로 설명했다.  

**회의에서 제시한 예시 흐름:**

```text
사용자: 우리가 사내 자체 개발 RAG 시스템을 개발 중입니다.

AI: 정확한 검토를 위해 다음 사항을 확인해 주세요.
Q1. 모든 사용자가 같은 Vector DB를 검색합니까?
Q2. 문서별 사용자 또는 부서 접근권한이 존재합니까?
Q3. 외부에서 업로드하는 문서가 포함됩니까?
Q4. 검색된 원문이 외부 LLM API로 전달됩니까?

사용자: 모두 Yes

AI: 보안 점검 우선순위
- HIGH: Retrieval Access Control
- HIGH: Indirect Prompt Injection
- MEDIUM: Sensitive Information Disclosure
```

> 위 문답과 우선순위는 회의에서 제시된 아이디어 예시를 기록한 것이며, 검증을 마친 보안 진단 결과나 팀의 확정 설계가 아니다.

**상태:** `추가 조사`

### 4.5. 팀원 E

이번 2차 회의 기록은 팀원 A~D의 발언을 대상으로 하며, 팀원 E 표기는 사용하지 않는다. 1차 회의의 익명 표기와도 인물 대응을 하지 않는다.

**상태:** `해당 없음`

## 5.1. 문화유산 굿즈 상품기획 지원

## 5.3. 길 안내 발전형

> **기록 구분:** 아래 `제안 내용`과 선택안 A·B는 팀원 개인이 제시한 오전 원안과 그에 대한 사전 분리 검토 내용이다. 이후의 현재 구체화안은 같은 개인 기획안을 회의 전에 발전시킨 내용이다.

### 제안 내용

- 목적지 주변 주차장과 경로 추천
- 주정차 금지·단속 위험 정보
- 리뷰 분석과 대체 장소 추천
- 그늘·우천 회피 보행 경로
- 초보운전자를 위한 교통 상황 설명

### 현재 확인한 장점

- 운전자·보행자가 겪는 문제를 직관적으로 설명할 수 있다.
- 모빌리티, 지도, 주차, 보험, 운전교육 등 B2B/B2C 확장 가능성이 높다.
- 완성도가 높으면 시각적이고 인상적인 포트폴리오가 될 수 있다.

### 제한 요소

- 주차, 단속, 리뷰, 그늘 경로는 서로 다른 데이터와 기술이 필요한 별도 프로젝트에 가깝다.
- 전국주차장 표준데이터만으로는 현재 빈자리를 판단할 수 없다.
- 과거 단속기록과 금지구역 데이터로 현재 단속 여부를 확정할 수 없다.
- 리뷰 작성자의 전체 이력 접근과 악성 여부 판정에는 약관·개인정보·공정성 문제가 있다.
- 그늘과 우천 경로는 LLM보다 GIS·3D 공간정보·경로 최적화가 핵심이다.
- 외부 지도 API 연동만으로는 LLM 프로젝트의 차별성을 설명하기 어렵다.

### 권장 분리안

#### 선택안 A — 목적지 기반 주차 대안 의사결정

- 한 개 시 또는 구로 제한
- 목적지·방문시간·요금·도보거리·접근성 기준 비교
- 실시간 빈자리 보장 제외
- 외부 지도 API는 경로 연결에만 사용
- LLM은 사용자 조건 해석과 추천 근거 설명 담당

#### 선택안 B — 초보운전자 상황 설명 RAG

- 비보호 좌회전, 회전교차로, 보호구역 등 공식 규칙 기반 설명
- 운전 전 학습 또는 운전 후 복습으로 제한
- 실시간 주행 중 조작과 법적 판단 제외
- 운전학원·보험사 안전교육·렌터카 업체를 B2B 후보로 검토

### 현재 사전 구체화안 — 오전 개인 기획안의 후속 구체화

> **특정 시설·장소 방문자를 위한 주차장·대중교통·관람정보 통합 방문·여행 계획 도우미**  
> 방문 일시, 이동수단, 관람시간과 동행자 조건을 분석하여 특정 시설 한 곳의 주차장·대중교통·관람정보·날씨·주변 장소를 결합한 방문 전 계획과 대안을 제공한다.

- 대상 시설: 박물관·미술관·관광시설 중 1곳
- 서비스 범위: 시설 반경 3~5km
- 이동수단: 자동차·대중교통
- 핵심 기능: 휴관·운영시간 확인, 주차장 후보 비교, 버스·정류장 정보, 날씨에 따른 계획 조정, 1시간·2시간 관람계획, 주변 장소 연계
- 데이터 처리: 관람 설명은 RAG, 시간·요금·거리는 정형·공간 DB, 날씨·버스·주차 잔여면은 호출 시점 API
- 실제 길찾기: 자체 경로탐색이 아니라 외부 지도 링크로 연결
- 제외: 전국 서비스, 자체 내비게이션, 현재 단속 여부 판단, 실시간 주차 보장, 리뷰 작성자 악성 판정, 그늘 경로 직접 계산
- 현재 상태: `사전 구체화 — 팀 합의 전`

### 점심 회의 확인사항

- [ ] 대상 시설과 서비스 지역은 어디인가?
- [ ] 해당 지역의 주차·버스 API가 실제로 제공되는가?
- [ ] 실시간 정보가 없을 때 어떤 대체 안내를 제공할 것인가?
- [ ] 자동차와 대중교통을 모두 MVP에 포함할 것인가?
- [ ] 주변 관광지·음식점 정보를 어느 범위까지 포함할 것인가?

### 회의 기록

- 선택할 세부 문제: 방문·이동 계획과 개인 맞춤형 문화유산 도슨트의 결합 가능성 검토
- 핵심 고객: 회의에서 확정하지 않음
- 핵심 사용자: 문화유산 여행자 방향이 제시되었으나 확정하지 않음
- 실시간 데이터 필요 여부: 회의에서 확정하지 않음
- 공식 데이터: 공식 문화유산 데이터 사용 제안
- LLM·RAG의 핵심 역할: 공식 사실·출처 검색, 사용자 조건에 따른 장소·설명 구성
- 제외할 기능: 회의에서 추가 확정하지 않음
- 차별성 우려: 현재 Gemini·ChatGPT만으로도 충분히 가능한 서비스가 아닌지 검토 필요
- 다음 검증 과제: 방문 도우미와 개인 맞춤형 문화유산 여행 도슨트의 결합 구조 및 범용 LLM 대비 차별성 정리
- 최종 상태: `통합`
